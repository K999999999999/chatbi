# ChatBI 新人项目导航 Spec

Status: 用户已于 2026-10-11 确认 Spec 和 Ticket 拆分；Design Review 为 PASS WITH MINOR FIXES，Ticket Readiness 为 READY；三个 Ticket 已连续实施，Ticket 03 等待非作者新人走查反馈。

## Problem Statement

仓库已有 README、Architecture、Product Scope、Runbook、Specs、Designs 和 Acceptance 等入口，且既有 `repository-structure-readability` 工作完成了基础 README、工作区地图和代码职责整理。后续产品能力持续增加后，新人仍需自行拼接产品功能与代码模块的关系；部分当前状态也有漂移，例如 README 对 R5 验收的描述、Runbook 对 R7 的阶段说明及 R7 Spec 的状态字段没有全部与最新验收事实对齐。在创建本工作项前，2026-10-11 的只读检查确认 Markdown 本地链接通过，Harness 检查 37 份记录且无 findings；这些检查不验证新人导航是否完整，也不替代代码或运行验收。

新人需要从产品全景逐层走到主要用户功能、工程子系统、关键代码入口、对应事实文档和验证方式，并能实际启动开发环境、检查健康状态和运行确定性软件测试。现有资料仍有价值，不应另建一套与正式 Spec、Runbook 或 Acceptance 竞争的事实源。

## 目标与预期结果

为新开发者建立连贯、可维护的项目导航，使其能够：

1. 从简短入口理解 ChatBI 的定位、产品边界、主要用户场景、端到端业务链路和当前项目成熟度；
2. 从全景按功能逐层定位负责的模块、目录、关键入口、行为 Spec / 实现 Design、测试 / Evaluation / Acceptance 及适用运行入口；
3. 区分产品代码、业务事实源、派生资产、验证证据和本机运行资产，知道需要以哪个事实源为准；
4. 按推荐的新 clone 路径启动本地开发环境，检查服务健康状态并执行确定性软件测试。

导航按“总览 → 功能与模块地图 → 主链路深读 → 运行和验证”的层级组织。关键入口和业务流程需要说明；普通私有函数通过源码阅读，不要求逐函数写说明。

## 范围

覆盖当前已实现的产品能力和仓库中的一级工程子系统，包括：身份与权限、自然语言问数与多轮查询、经营分析、结果展示、历史与成果、执行状态与流式反馈、导出、Semantic / Structure 事实、RAG 在线与离线链路、Bootstrap、Observability、Evaluation、数据库、前后端、Scripts、本地运行保障、测试与 CI。未实现计划和已退役入口需标成计划 / 历史，不能混入当前能力。

导航需要建立可检查的关系：

```text
产品能力 / 工程职责
  → 主要用户或维护场景
  → 所属模块、目录和关键代码入口
  → 权威 Spec / Design / 数据事实源
  → 对应 Software Test / Evaluation / Acceptance
  → 适用的 Runbook、开发或验收命令
```

可以在审查证据表明文档放错职责位置、造成重复权威来源或难以发现时，执行有范围的文档移动或合并；移动前核对引用与历史语义。

## 已确认决策与约束

- 目标读者是首次接手本仓库的新开发者；目标是理解整个项目并能继续深入源码，不是终端用户操作手册。
- 覆盖面包括产品功能和工程子系统，而非只列用户直接可见的页面功能。
- 覆盖清单依据当前仓库的一级模块、实际用户能力、已确认产品范围和适用事实文档形成；每个当前功能 / 子系统都应有导航归属，未来计划和历史退役能力需单独标识。
- 代码导航粒度为每个主要模块 / 目录及关键入口、重要业务流程；不为普通私有函数和每行代码单独维护说明。
- 新人基础动手路径包含推荐容器开发入口、服务健康检查和确定性软件测试。真实浏览器完整业务验收与真实 LLM Evaluation 作为进阶路径链接说明，不是首次上手的必跑门槛。
- 保留 `AGENTS.md`、Architecture、Product Scope、Specs、Designs、Runbook、Acceptance、`.scratch/` 各自职责；导航优先链接权威事实，不复制完整 Contract 或历史报告。
- 基于当前证据修正仍被当作当前事实的过期状态和路径描述；日期化历史 Acceptance 保持原样，不将旧结果改写成当前候选证据。
- 文档位置应服务职责和查找路径，不为了目录整齐批量迁移。

## 验收条件

1. 新人走查清单可由非导航文档作者独立执行并留存结果：从项目入口说明产品用途、支持边界和成熟度；沿导航定位主要功能、关键架构和核心查询链路；区分开发运行、本机稳定运行与公网生产就绪状态；定位推荐启动、健康检查和确定性测试入口。清单不得把口头补充作为通过条件。
2. 每项主要产品能力和工程子系统都能从导航定位到负责人模块 / 目录与关键代码入口，并进一步找到适用的行为事实源和验证入口；不要求对无独立行为 Contract 的内部工具凭形式补建 Spec。
3. 至少一条代表性在线查询链路可从 Web 入口追到 API、Application / Domain、Retrieval / SQL Guard、数据库和结果返回，并能定位相应测试 / Evaluation / Acceptance；其他主要功能有明确的专题路线或所属关系。
4. 新 clone 的推荐开发路径清楚列出前提、初始化顺序、配置边界、启动、健康检查及确定性测试命令；进阶验收明确标注额外依赖和历史候选证据边界。
5. README、导航页、架构地图、Runbook、Roadmap 与实际主要目录和当前事实一致；发现的过时状态已修正或明确标为历史 / 候选绑定事实。
6. 所有导航本地链接有效，目录、模块职责和关键入口引用与当前仓库核对一致；验收报告说明无法在当前可用环境复现的步骤，不把文档检查称作业务验收。
7. 用户本机配置、Secret、现有开发 / Stable 数据和运行资产不被读取后公开、覆盖、移动或清理；工作范围不包含业务源码和运行行为修改。

## 验证方式

- 只读盘点现有根目录、源码、前端、数据库、脚本、测试、评测、文档与部署入口，逐项核对导航关系。
- 执行仓库 Markdown 本地链接检查及适用 Diff 检查。
- 通过新人阅读路径走查验证从概览到功能 / 代码 / 契约 / 测试 / 运行入口没有关键断点，并抽查代表性业务流的实际调用顺序。
- 在不接触现有 Stable / 用户数据的隔离新 clone 或等效隔离开发环境中核对并执行推荐启动、健康检查和确定性软件测试；是否能在执行环境满足前提时复现必须如实记录。
- 不把真实 LLM Evaluation、完整浏览器验收或生产运行核验作为本导航改动的默认软件测试。

## 不在范围内

- 改变产品功能、业务规则、Authorization / State Contract、公共 API、模块职责或依赖方向。
- 重排或重构业务源码、测试实现、数据库结构、部署实现或运行脚本。
- 移动数据、模型、`.env`、本机配置、Stable / Dev 资源、报告或日期化 Acceptance 证据。
- 大规模迁移文档、删除历史资料、复制正式 Contract / Acceptance，或逐函数编写注释。
- 宣称 ChatBI 已完成公网生产部署、通用多租户 / 多数据库能力或 Production Ready。
