# 会话入口与工作阶段恢复 Spec

Status: confirmed

## Problem Statement

新会话容易丢失上次工作的阶段、决定和下一步；未提交改动可能被误当成新需求的内容。当前仓库把 `ask-matt` 作为工程请求的必经路由，但它只推荐 Skill 后停止，不能表达“用户尚不知道要什么”的需求发现过程。小改动也没有稳定的意图记录，导致 PR 合并后难以回看原始目标。

## Goal

让 Codex 在每个 ChatBI 仓库新会话开始时，基于当前 Git 状态和仓库内工作记录识别工作阶段，简短告知用户当前状态，并能从中断处安全恢复，避免遗漏、混入无关改动或项目目标漂移。

## Users and Scenarios

- 用户开启新会话，继续一个正在澄清、等待 Spec 确认、等待拆分、实施或验收中的工作。
- 用户开启新会话，但当前工作区有未提交或未归属的改动。
- 用户只知道一个问题或机会，还不知道要实现什么。
- 用户目标明确，但关键行为、范围或验收条件尚未确定。
- 用户提出一个小型工程改动，期望留下简短记录并直接实施。
- 用户提出跨阶段或复杂工程改动，期望先确认完整 Spec，再拆分执行目标。

## Proposed Behavior

### Session entry

- 每个进入 ChatBI 仓库的新会话，首个工程响应先检查当前目录、分支 / worktree、`git status` 和未完成工作记录。
- 根据检查结果输出简短状态栏：当前阶段、工作项、工作区状态、上次停点和下一步。只读咨询也标明“只读咨询 / 无实施阶段”。
- 以实时 Git 状态和工作记录为依据；两者冲突或记录缺失时明确报告“状态待确认”，不推断为已完成或干净。
- 工作区有改动时列明并判断归属。属于当前活动工作项的改动可在说明后恢复该工作；归属不明或属于另一工作项时，暂停新的写入操作，先让用户决定如何处理。不得自动清理、覆盖、提交或挪动用户内容。

### Work stages

- `需求发现`：用户描述问题 / 机会但没有确定方案或目标；整理现状、可能目标和选项，不假装需求已明确，也不实施。
- `需求澄清`：用户已有候选目标；查证项目事实并解决会改变范围、行为、边界或验收的重要歧义。
- `Spec 待确认`：已形成短或完整 Spec 草案，等待用户确认。
- `待拆分`：复杂工作 Spec 已确认，等待设计审查、Ticket 草案审查及用户确认拆分。
- `待实施`：小工作 Spec 已确认，或某个已确认 Ticket 可开始实施。
- `实施中`、`验证 / Review`、`PR 检查中`、`已合并待 Harness 复盘`、`完成`：分别反映实现、验收、PR 检查、合并后复盘和工作项关闭。
- 需要用户决定时标记 `等待用户决定`，并指出具体问题和阻塞的下一步。

### Work records and size-based flow

- 每个已确定要实施的工程改动均创建仓库内工作记录。活动工作项使用 `.scratch/<slug>/status.md` 记录阶段、分支 / worktree、已确认决定、未决问题、完成进度、关联路径和下一步，以及对应 Spec / Ticket 路径；完成后标记 done 并保留记录。
- 新会话优先匹配当前分支 / worktree 对应的唯一活动记录。若无匹配记录但有多个候选，或存在多个匹配项，则列出候选并请用户选择；不得根据旧聊天或目录名猜测。未完成的历史工作可在恢复时补建状态记录。
- 小改动使用短 Spec，至少写明目标、预期结果、验收方式和验证方式；确认后可直接实施，不要求拆 Ticket。
- 大型 / 多阶段改动使用完整 Spec；用户确认后经过设计审查，再拆为 Tickets、执行 readiness review 并由用户确认拆分，然后实施。
- 需求发现阶段可先创建状态记录，目标形成后再创建 Spec；纯问答、只读调查或未决定实施的探索不强制创建正式 Spec。
- 阶段改变、重要决定、交接或会话结束前更新 `status.md`，使新会话无需依赖旧聊天恢复。
- PR 已合并后，按 Harness 复盘检查项目背景、规则、工具或验证方式是否导致误解、漏验、返工或用户纠正；没有缺口时记录“无新增缺口”，有缺口时创建独立 Harness 改进项。此规则属于本次范围，当前基线尚未包含。

### Skill boundary

- `AGENTS.md` 直接规定自动会话入口、状态播报、Git 检查和恢复规则；不能依赖用户手动调用 Skill 才运行。
- 外置 `engineering-workflow` Plugin 增加独立的 `workflow-discovery` 需求发现 Skill；现有 `workflow-grill-with-docs` 继续处理已有候选目标的歧义；`workflow-to-spec` 支持短 / 完整两种产物。Plugin Skills 继续保持 manual-only；新会话自动判断和状态播报由仓库 `AGENTS.md` 执行，不依赖自动 Skill 调用。
- 新项目安装 Plugin 本身不会更改项目规则。用户在新项目手动运行 `setup-engineering-workflow` 时，该 Skill 应把会话入口 / 状态恢复规则纳入项目适配建议；仍须先检查项目现有约定并由用户确认要修改的文件，再写入项目 `AGENTS.md`。
- `ask-matt` 保留为可选的“推荐下一步”路由器，不再是每次新会话必经入口。
- 新流程继续使用 `Ticket` 指代有范围、验收标准和状态的可追踪实施工作项；`Target` 表示要达到的目标，不作为工作项名称。既有历史 Ticket 记录保持原样。

## Out of Scope

- ChatBI 产品运行时行为、业务 Contract、系统架构边界。
- 自动 stash、reset、checkout、commit、push、创建 PR 或 merge。
- 每条日常对话都创建工程工作项或 Spec。
- 在没有用户确认 Spec / Ticket 拆分前直接实施多阶段 Feature。

## Acceptance Criteria

- 新会话能先检查 Git / worktree 与活动工作记录，并按当前分支 / worktree 唯一匹配状态记录，用紧凑状态栏说明阶段、上次停点和下一步；匹配不唯一时向用户列出候选。
- 有未提交改动时能列出并分类；无法确认归属时暂停新写入，不丢失或混入改动。
- 无活动工作项时能区分需求发现、需求澄清、Spec 待确认及可实施状态；需求发现和需求澄清不会被合并成同一阶段。
- 小改动可通过短 Spec 记录后直接实施；复杂工作遵循确认 Spec、设计审查、Tickets 拆分与确认、实施的顺序。
- `status.md` 足以让新会话从已记录的分支 / worktree、阶段、决定和下一步恢复，不依赖原聊天内容。
- PR 检查中与已合并待 Harness 复盘是不同阶段；合并后复盘结论和后续改进项均有记录。
- Plugin 对应 Skill 和 README 与新的阶段定义、调用边界和 `Ticket` 术语一致；`ask-matt` 不再被仓库规则强制为必经入口。
- `setup-engineering-workflow` 说明安装 Plugin 不会自动改变仓库；显式运行时会提出适配后的新会话入口规则，并继续遵守先审查、后经用户确认再修改的门禁。

## Decisions and Open Questions

- 本 Spec 采用 `Ticket` 作为可追踪实施工作项的术语；`Target` 保留“目标”含义。历史 `.scratch/*/issues/` 和既有 Ticket 文件保持原样。
- 工作区有改动但明确属于当前活动工作项时，恢复该工作，不强制先把它清空；其他未归属改动需用户决定后才能开始新写入。
- 本 Spec 覆盖 ChatBI Harness 与外置 Plugin 的协同修改，并包含此前已确认但尚未合入的 PR 合并后 Harness 复盘规则；实施前须分别遵守两个仓库的规则，并保持两边变更边界清楚。

## Verification Direction

- 文档和 Skill 名称 / 链接检查。
- 用干净工作区、活动工作项、未归属改动、发现需求、待确认 Spec 和已确认大需求等情境做流程走查。
- 本项是 Harness 流程与文档改动，不需要运行 ChatBI 产品测试；若实施中新增可执行逻辑，再按其实际风险补充验证。
