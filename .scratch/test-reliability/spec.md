# 测试可靠性与运行路线精简

Status: confirmed；七项 Ticket 已实施并随 PR #86 合并（2026-10-15T16:28:38Z）。最终托管 CI 结果及文档收尾见 [工作状态](status.md) 和 [路线图收尾 Spec](../test-reliability-roadmap-closeout/spec.md)。

## Problem Statement

项目以源码作品开发和展示为当前用途。用户在本轮逐项审查讨论中决定：移除独立 APP 打包运行路线；保留本地开发测试与 CI；修复已复现的测试可靠性问题，并统一测试和评测证据的可追溯信息。

本 Spec 固化本轮需求，不把讨论中的“明白 / 可以 / 继续”当成已经完成修复，也不把局部记录缺口推断为历史报告全部错误。后续代码实施须经过完整 Spec 确认、Design Review、Ticket 草案与 Readiness Review、拆分确认及实施授权。

## 事实与证据基线

- 仓库：`github.com/K999999999999/chatbi`；本轮调查基线为 `47a9dc8cee10298504d9daec6be79712a5bf194d`。整理前本地 master 与远端 master 同 SHA，工作区干净。
- 已盘点 134 个 Python 测试文件、18 个前端测试文件、四套 AI 评测案例、dev 入口、相关脚本及 CI。盘点和定向核查不等于每个可能边界都已得到证明。
- 本轮基线运行：Python 979 passed / 51 skipped / 142 subtests passed；浏览器 67 项及 Vite 代理 1 项通过；真实 PDF renderer 2 项通过；完整 `./dev check` 通过。
- 数据库 CI fixture 5 项通过；development 套件的历史锁测试在失败清理时挂起。取消本次隔离库中该条等待查询后，输出该测试断言失败，其余 52 项通过。尚不能据此判断业务保存逻辑有缺陷，也不把首次未及时观察到锁等待的原因当成已经查明。
- 首次改密浏览器测试使用 `./dev test web auth.spec.ts --grep 'first password change' --repeat-each=2` 复现一次通过、一次失败；失败证据保存在本机 ignored 的 `reports/tests/chatbi-test-web-101203-22021/`。
- 无序数值比较在现有 `1e-6` 误差下，用 actual `[0.0000009, 0]` 和 expected `[0, 0.0000018]` 复现失败，反转 actual 后通过；存在完整配对但当前贪心算法会误判。
- 本机 `chatbi-app:local` 的查询理解代码与基线源码 Hash 不同，镜像 revision 为 `unknown`；标准应用验收直接把宿主 HEAD 写入报告，未核对镜像源码身份。未执行完整 APP 验收，未证明已经发生错误通过。
- 普通 CI 没有执行 development 数据库套件和真实 PDF renderer；语义评测报告缺少案例内容指纹与部分模型配置；多轮 / 经营分析结束后才读取 Git 身份；报告名称精确到秒且现有写入允许覆盖；语义案例实际 7 个，文档仍写 6 个。
- 同秒报告重名已经构造验证；没有证据证明历史报告已被覆盖。RAG 路径问题主要涉及将移除的 APP 验收，不扩展为已经证实的 dev 问数故障。
- 本轮未运行真实 LLM 或完整收费容器业务验收。此前其他工作项的通过记录仍只属于各自基线。

## Solution

以 dev 为唯一支持的开发、运行、展示与测试路线。软件测试在本地用于即时反馈，在 CI 中自动重复必要检查；真实 AI 评测及完整业务验收按需手动触发。日常源码测试不以重新打包应用为前置步骤。

修复测试自身的资源释放、数据隔离和结果比较；所有测试 / 评测报告按实际依赖记录复现信息，保留每次运行的独立证据。优先复用现有测试框架和报告，不建设新的测试管理平台。

## User Stories

1. 开发者使用 dev 修改和测试源码，无需另行维护 app 的构建、初始化和验收路线。
2. 数据库并发测试即使失败，也能报告原因并释放测试资源，不无限等待。
3. 同一浏览器测试可重复执行，每次从正确的账号状态开始，不污染日常账号。
4. 结果内容在允许误差内相同且不要求排序时，行顺序变化不改变评测判分。
5. 提交 PR 后，CI 自动验证关键软件行为；真实 LLM 调用不混入普通 CI。
6. 阅读报告时可以查明测试版本、范围、依赖身份和执行结果；运行中代码变化或报告写入冲突不会被掩盖。

## Implementation Decisions

### 运行路线与边界

- 移除 `./dev app`、`./dev verify app`，以及 doctor / recover-admin / Bootstrap / 维护工具中专属的 app 目标和帮助说明。已移除目标的调用应在资源操作前明确失败，不能静默转到 dev。
- 移除专属应用 Compose、APP 验收脚本、仅为独立应用打包存在的根 Dockerfile、专属测试及失效配置引用。逐项核对消费者后删除，不按名称误删 Python `app` 对象、Web 应用、`chatbi_app` 数据库角色或公共功能。
- 保留阻止 dev 维护工具误操作旧 APP 资源的拒绝规则；不把移除正向支持解释为取消资源身份校验。
- 保留开发 Dockerfile、Docker / Compose、Dev Container、业务数据库、开发资源身份、源码挂载及热更新；保留 dev 的环境管理、初始化、账号恢复、安全检查与日常测试能力。
- 保留 `./dev verify dev` 的隔离业务验收及显式 real 模式，均仍是按需执行，不成为每次源码测试的前置步骤；保留手动 Real E2E 与 AI Evaluation。
- 不自动删除本机 APP / dev / 旧 Stable 的镜像、容器、卷、配置、账号或资产。仓库删除由 Git 保存历史；独有历史文档 / 验收记录保留，并修复受影响的引用。
- 不改变首次登录改密、账号权限、业务 API、SQL Guard、指标定义或模型提出候选 / 程序裁决的边界。

### 测试正确性与隔离

- 数据库并发用例在任一断言、超时或 worker 异常路径上，先安全释放自己持有的锁，再等待 worker 退出；所有等待与清理均有明确上限，保留原始失败原因。不能通过跳过用例、弱化断言或仅延长等待来掩盖问题。
- 锁观察应确认目标测试会话的真实等待，不以任意其他会话的等待替代证据。验证成功、未观察到等待、worker 异常与清理路径；必要诊断仅使用专属隔离测试数据库。
- 首次改密测试每次获得独立、可识别、处于初始状态的测试账号。正常与失败路径均执行清理；复用既有测试装配入口，不新增面向真实用户的测试后门。
- 无序比较要求：若存在满足现有逐列比较规则的完整一一配对，则通过；不存在则失败。保留重复行数量、NULL、列顺序、截断规则及原数值绝对 / 相对误差；有序比较仍逐行判断。不修改标准 SQL 或案例答案来适应比较器。

### 本地与 CI

- 保留 `./dev test python/database/web/renderer/all` 与 check 的本地用途。CI 运行相同范围的关键软件检查，不另写一套业务判定逻辑。
- 普通 PR CI 补齐现有 development 数据库套件及真实 PDF 渲染；现有 Python、SQL Guard、浏览器、质量和安全检查继续保留。
- CI 使用临时数据库、测试账号及渲染资源，明确启用对应测试开关；必须能辨别实际执行与 skipped，不把未执行写成通过。失败非零退出，保留足以定位的结果证据。
- 普通 CI 不需要业务应用镜像打包或上传，也不调用真实 LLM。开发 / 测试环境镜像作为依赖环境仍可使用。
- 不改 GitHub 分支保护或远端仓库设置；如新增 job 需要远端设置配合，交付时单独说明具体影响。

### 所有测试与评测的可追溯信息

- 软件测试 / 质量检查以一次入口命令或 CI job 为记录单位，至少能识别独立 run、执行范围 / 参数、代码身份、起止时间、适用运行环境、退出结果，以及实际可得的通过 / 失败 / skipped / 未执行范围。无法取得的计数明确记为未知，不推算成通过。
- AI 四套评测均记录代码身份、实际测试集内容 Hash、模型名、脱敏服务指纹及有效生成参数。经营分析 Judge 等额外模型调用记录其自身适用配置，不能用业务模型配置冒充。
- 只有实际依赖数据库 / RAG 的运行，才记录对应数据指纹、算法、摘要、RAG 发布身份与必要上下文指纹。保留当前已有效的记录，不要求无模型软件测试填写模型参数，也不要求纯语义评测连接数据库。
- 复用现有日志、机器可读报告及 CI artifact；补足缺少的命令级证据，不要求每个测试函数新增独立日志或建设通用平台。报告最小字段和适配方式在 Design Review 中收敛。
- 开始前记录 HEAD 与 dirty，结束后复核；同时核对实际使用的测试集 / 上下文等适用输入身份。报告保留开始、结束与一致性结论，不能只用结束时的状态命名整个运行。
- 检测到变化时可保留诊断结果，但必须明确运行中变化，不能作为固定 clean candidate 的正式验收证据。Git 无法读取、应有指纹无法核实时明确失败 / 未确认，不伪装成 clean。
- 起止一致性检查不能证明期间从未发生改动又恢复；不建立文件监控或把起止检查宣传为完整不可变执行环境。
- 每次运行采用独立编号。报告写入禁止覆盖已有路径；重名或写入失败明确报错、非零退出，旧报告字节保持不变。JSON / Markdown 使用相同运行身份，部分写入失败不能报告完整成功。
- 禁止覆盖针对已发布的最终证据；同一次运行的私有目录可以更新内部进度、恢复及清理状态，结束后再生成不可覆盖的最终报告。两者不得混淆。
- 报告不能记录 Secret、完整连接串或未经脱敏的内部端点；原始敏感模型输入 / 输出不因补追溯信息而进入普通日志。

## Compatibility 与 Documentation

- app 路线有意停止支持；在 README、Runbook、Product Scope、Architecture、相关容器 / Bootstrap / 账号恢复 Contract 中同步删除现行承诺，并更新 Roadmap 中受本次确认影响的当前描述。
- 现行 APP Contract 的独有历史内容归档到本工作记录的 history 或沿用已有归档；历史验收保持原提交与范围，不能改写成 dev 或本目标结果。删除路径的本地链接须修复。
- 评测报告优先增量补字段，保留历史报告可读性；旧报告缺少本次新增证明时标为不可确认对应新要求，不回填虚构的参数 / 指纹，不自动改写旧分数。
- 保持既有 suite 名称、case ID、数值容差与有效比较边界；正式验收器对新生成报告核对适用身份和运行一致性。
- 当前语义案例数以案例文件为准，修正文档 6 / 7 的差异；其他套件不机械扩题或改答案。

## Testing Decisions 与验收

1. 移除 APP 后：help 不再宣传 app；旧 app 目标在副作用前失败；dev 的帮助、定向测试、维护 / 恢复目标选择和 Compose 结构回归通过；无误删公共消费者或本机资源。
2. 锁测试正常路径通过；故意触发失败 / worker 异常时能在上限内退出，锁及专属资源释放，命令非零并保留原始失败信息。重复隔离运行不挂起。
3. 首次改密用例连续执行至少两次都通过；正常与失败清理均有证据，不依赖同一账号的前次状态。
4. 无序容差重叠样例、行置换、重复行、真实不匹配、NULL、边界误差及有序模式有确定性回归；保持现有业务案例语义与比较标准。
5. CI 定义确实调用 development 数据库和真实 renderer；本地使用相同套件验证。远端 CI 未执行时标为未执行，不能仅凭 YAML 推断托管运行成功。
6. 各类报告验证适用字段：模型 / 数据不适用时不虚构；模型设置或题目内容变化可区分；代码 / 输入变化和 Git 读取失败不能形成正式 clean 证据；原有报告展示与比较行为继续可用。
7. 同时刻、同提交、同套件多次写入仍产生独立证据；强制同名失败时不覆盖旧文件；写入失败返回非零。
8. 正式文档、案例数量、归档与本地链接一致；完整 `./dev check`、适用全量软件测试、最终 Code Review 和 Diff 检查通过。
9. 仅比较器、报告元信息、测试装配与 CI 变化时，优先使用确定性证据验证，不为证明本目标而自动发起真实 LLM 费用或操作日常环境。若实施影响正式 AI 业务行为，先明确影响与所需验证授权。

## Out of Scope

- 需求澄清阶段仅整理需求；后续用户确认完整 Spec、七项 Ticket 及实施授权后，按此范围完成实现与交付。该历史阶段未操作服务或数据库。
- 不接手 `fix/full-validation-findings` 旧候选，不混入它与当前指标原话 Contract 冲突的语义断言；按原记录保留 branch / worktree。
- 不新增产品业务能力、发布平台、镜像仓库、部署流水线、测试管理平台、容量承诺或新的付费评测门槛。
- 不取消首次改密或放宽权限 / SQL 安全 / 评分标准，不因发现边界缺陷就判定历史结果无效。
