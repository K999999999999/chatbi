# Harness 任务控制与持续维护 V1

Status: confirmed
Stage: 实施与本地验收；Ticket 拆分和本地实施授权已于 2026-10-19 确认
Owner: 当前主 Agent；确认后由当前工作项的唯一 writer 维护
Baseline: ChatBI `2897302038fa42167e79a0b5ad483c2b628359b9`

## Problem Statement

当前 Harness 有阶段 Skills、项目规则、长期记录、本机实时状态及 CI，但缺少完整、可核实的阶段转换控制。Agent 可以填写状态，却未必提供足够的进入 / 退出依据；用户难以持续判断实际 Diff、范围变化、诊断进展和何时需要介入。部分任务发生长时间反复修改、文档收尾事实过期和验证证据难以恢复。

本目标改善 AI 工程工作的可见性、可控性、恢复能力与维护效果，不改变 ChatBI 产品行为，也不承诺消除所有错误或所有越权路径。

## 已确认决定与授权

以下决定来自当前会话逐项确认；用户随后已对本 Spec 回复“确认”。确认覆盖需求 Contract，不自动授权实施或远端操作。

1. 通用能力归 `engineering-workflow` Plugin，ChatBI 保留项目适配并作为首个完整验证项目。
2. 第一版以工具管理状态、校验转换和收集事实；Agent 执行与反馈；GitHub 执行远端门禁。不建设独立后台监控、强制中断、数据库或管理界面。
3. 正常实施切片完成后汇报并继续；新增依赖、改变公共接口 / 权限 / 数据规则、扩大范围、降低验收标准时停止相关变更，等待用户决定。
4. 同一问题连续 3 轮诊断无实质进展，或连续 30 分钟没有新增有效证据，任一触发则停止继续修改并升级反馈。预算跨会话保留，重复命令、改名和切换会话不能清零。
5. 发布前展示最终候选、Diff、风险和验证证据，由用户在聊天中明确批准。高风险候选的人工批准第一版仍是流程约束，不建设独立 GitHub 审查身份 / App。
6. 新项目显式初始化后自动准备适用配置；已有项目优先复用并展示差异；远端配置须明确授权后应用、读回核验。安装 Plugin 本身不修改项目。
7. 动态文档、交接恢复、证据有效性及 Harness 自身维护属于同一目标；优先复用现有机制，不以增加规则和检查数量作为效果证明。

当前授权覆盖需求整理、已确认 Spec 后的 Design Review 与 Ticket 草案 / Readiness；不构成产品或 Harness 实施、Plugin 安装更新、付费调用、Push / PR、远端设置修改或失败注入实验授权。Ticket 拆分须确认，并明确实施范围。

## 事实与 Canonical Source

- ChatBI 的现行约束以 [AGENTS](../../AGENTS.md)、[工作项规则](../../docs/agents/issue-tracker.md)、[交付规则](../../docs/agents/git-pr-workflow.md)和[文档规则](../../docs/agents/documentation.md)为准；本草案确认前不替换它们。
- 任务实时进度保存在 Git 返回的公共目录 `harness/work-items/<id>/status.md`；长期 Spec、Tickets、决定和验收在项目约定位置保存。Git / PR / 实际验证是对应事实的权威来源，状态记录不替代它们。
- 当前 ChatBI 检查工具只读检查部分字段、引用、Ticket 及 Git 状态，不验证完整 Stage 转换、远端正文或任意语义事实。
- Plugin 目前以阶段 Skills 和规则为主，没有独立状态执行器。安装缓存不是源文件修改位置。
- 当前登记的 Marketplace 源为 `agent-plugins-codex-harness` linked worktree；2026-10-19 核实其 HEAD 为 `9d97431b0e8d3870db5d06c748a23ddae6a2d1cd`，分支为 `feature/harness-workflow-control`。源目录存在用户未跟踪的 `engineering-process-audit.7z`，不得纳入、覆盖、移动或清理。
- ChatBI 本机原工作项 `long-task-progress-clarity` 提供长任务沟通问题的发现依据；它尚未授权实施。本目标使用独立 ID，关联不继承授权，不提前把旧工作项标为解决。
- 远端最近核实存在 8 项指定 Actions 来源的必需检查；严格更新分支尚未开启。通用 Plugin 不硬编码这 8 项名称；ChatBI adapter 依据当次远端事实定义。

## Solution 与范围

交付可复用的任务控制工具和阶段规则，在 ChatBI 完成适配和验证。通用机制描述工作项身份、状态、证据、预算、Diff、授权、维护与接入行为；业务项目拥有自己的命令、文档、风险路径、验证集合和远端规则。

第一版覆盖：

- 状态查看、证据核对、合法转换、交接和恢复。
- 本轮与累计改动说明，以及授权范围变化识别。
- 有界诊断、进度反馈、停止和人工接管。
- 本地 / CI / Evaluation 责任及证据失效规则。
- 动态文件登记、适用性核对及合并后收尾。
- 新 / 既有项目接入与远端配置差异核验。
- Harness 缺口追踪、效果验证、例外复查和机制退出。

### Change Profile

这是跨 ChatBI 与 Plugin 两仓库的长期工程机制变更。风险集中于状态误判、授权扩大、证据失配、工具失效、用户改动覆盖和错误放行；业务应用代码不在范围内。任务记录使用唯一主记录与关联记录，不将两仓库进度视为同一提交状态。

## User Stories

1. 用户随时询问状态时，能得到当前阶段、已完成内容、剩余工作、阻塞 / 等待对象及下一步，而非仅收到工具执行细节。
2. 用户能看到每个完整行为切片和整个目标的实际改动，及时判断是否偏离已确认目标。
3. Agent 无法解释失败或长期没有定位进展时，会保留成果并交还决定权。
4. 新会话能依据记录和真实 Git / PR 恢复，不因当前分支、旧摘要或 clean 状态误判完成。
5. 项目接入时由 Agent 准备 CI 与维护机制，用户无需自行想到和逐项添加检查。
6. 任务完成后文档与记录反映真实结果，历史证据仍绑定其原始版本。
7. Harness 的重复问题进入有效改进，失效和冗余机制能够退出。

## Observable Behavior

### 1. 状态与流转

状态查看至少展示：工作项及仓库身份、主阶段、运行情况、Owner、适用基线 / 候选、已确认范围、授权依据、最近有效证据、预算、阻塞、上次停点和可执行下一步。运行情况须区分执行中、等待工具 / CI、等待用户、真实阻塞及显式暂停；不把等待或本地完成混同整个目标完成。

阶段及转换以项目适配的 Contract 定义，最少支持以下语义，不要求小任务走不适用的复杂阶段：

| 转换 | 进入依据 / 退出条件 |
| --- | --- |
| 需求形成 → 可实施 | 稳定范围、可观察验收、适用设计 / 拆分确认及实施授权 |
| 实施 → 验证 / Review | 本轮改动与候选身份明确，适用检查范围已列明 |
| 失败 → 继续修复 | 失败证据、原因假设、有界动作、剩余预算；未改变已确认决定 |
| 验证 / Review → 待发布 | 适用验证、Diff Review、动态文件核对完成，例外已明确 |
| 待发布 → PR 跟进 | 目标、范围及发布授权明确，候选身份与证据相容 |
| PR 跟进 → 已合并待复盘 | 远端确认实际合并，不以 CI 绿色或命令成功替代 |
| 已合并待复盘 → 完成 | 复盘、文档 / 关联状态核对、已决定清理完成，遗留项有准确处置 |

校验失败时转换命令非零退出，保留原状态及拒绝原因；不得先写成功状态再补证据。事实不可读取、版本冲突或记录损坏时标未知 / 待核实，不猜测、不继承未知授权。

工具应优先复用可确定采集的事实；无法自动证明的用户决定、语义 Review 等须保留来源与核实人，不伪装成机器验证。状态写入遵循单 writer、写前核对和原子更新；冲突不覆盖后来记录。

**强制边界：工具能拒绝经过它的不合法转换，不能阻止绕开工具的 Shell / Git 操作，也不能在 Agent 卡住时保证停止。** 安装 Plugin 和填写状态均不等于执行环境获得隔离或授权强制。

### 2. Diff 与人工介入

每个有意义的行为切片完成后，展示本轮基线到候选的变化及任务起点以来的累计变化，包含：

- 原来 / 现在的可观察行为，新增、修改、删除的模块与入口。
- 可核对的 Git 基线、候选、Diff / 文件入口；未提交改动明确标注，不能仅报告已 Commit 部分。
- 依赖、接口、权限、数据、配置、测试 / 阈值及验收变化。
- 实际覆盖、失败、未运行检查、残余风险及下一步。

文件数与增删行数只作辅助，不作为风险或正确性的证明。正常切片汇报后继续，不增加逐文件 / 逐 Ticket 用户批准。

发现新增依赖、改变公共接口 / 权限 / 数据规则、扩大范围或降低验收标准时，停止相关变化，展示影响后等待用户决定。其他无冲突工作只能在原授权和预算内继续。

人工批准绑定具体可审查候选、目标仓库 / 分支及所说明范围；实质变化后旧候选批准不自动有效。区别范围授权与候选证据：同范围 CI 修复及收尾仍受持续授权覆盖，必须更新 Diff / 验证；涉及上述关键变化时重新取得决定，不能借“CI 修复”扩大范围，也不把每次 Commit 都当成必须重问授权。

### 3. 有界诊断与反馈

同一问题连续 3 轮诊断无实质进展，或连续 30 分钟没有新增有效证据，任一触发则停止继续修改并升级反馈。

一轮诊断包含原因假设、验证动作和观察结果。实质进展包括有依据地缩小故障范围、排除假设、取得可复现案例或验证修复；新增代码、重复已有输出、重复重跑相同命令不算进展。进展必须引用证据并留下预算更新依据，不能由无依据“有进展”文字清零。

预算记录绑定问题身份，切换会话、改名或同问题分支切换不清零；中断和计时不可核实时标未知并复核，不当作已获得新预算。用户显式暂缓期间不在后台继续执行；正常构建 / 测试 / CI 等待与诊断耗时分开记录，仍须有可核实的开始、预期等待 / 超时和下一检查条件，不用无限等待规避预算。

触发后保存可靠候选、未提交改动和失败证据，反馈已完成内容、失败点、尝试、新证据 / 未知及下一步成本，等待用户决定。不得自动 stash / reset / 回退用户改动或以删除证据掩盖失败。反馈遵循会话已有频率约束；本目标不放宽“不超过 60 秒无有意义进度更新”的要求。

### 4. 验证、证据与 CI

每项行为变化必须说明由何种 Software Test、AI Evaluation 或 Business Acceptance 验证，本地与 CI 覆盖及不适用原因。测试、Fixture、skip、Mock / 真实依赖、退出码和完整通过状态须区分；CI 绿色数量不是验收充分性的证明。

验证证据关联候选、基线、覆盖范围、输入及运行身份。代码、base、模型、数据、RAG、配置或案例变化后，判断受影响证据是否失效；相容证据可以复用，必须记录边界，不能把旧报告改写成新提交运行结果。评测 / 云端证据不足时保留未验证，不靠付费调用自动补齐。

ChatBI 适配准备启用严格更新分支，保留当次实际必需检查及可信来源。目标分支移动后，旧组合上的成功不能单独满足新组合要求；不得混淆“必需检查”和其他成功 job。远端应用仍须授权并读回核验。

高风险候选第一版由用户聊天批准；不创建独立审查身份 / App。**门禁自修改的独立远端保护仍未完成，不能因此把 Harness 自动合并判断升级为无条件 READY。** 分类与记录仍可能被相同写入身份修改，需明确残余风险。

### 5. 动态文档与完成条件

每个项目维护一份权威的动态文件清单，登记职责、更新事件、Owner、权威来源、历史去向及核对方式；项目 Agent instructions 链接它，不复制完整规则。

| 记录 | 触发事件与更新范围 |
| --- | --- |
| 本机工作项实时状态 | 阶段、决定、验证、PR、阻塞、交接及清理变化；当前字段与 Next |
| 长期 Spec / Ticket / 决定 | 已确认长期决定、Ticket 状态、结果、验收与遗留问题 |
| 长期 status 快照 | 按需保存规划与历史，明确不竞争实时状态权威 |
| Roadmap | 已确认目标、依赖、验收或完成事实变化 |
| 正式 Spec / Design / Architecture / Product Scope | 对应行为、机制、职责或支持边界变化 |
| Runbook | 命令、配置、运行、诊断及恢复步骤变化 |
| README / Agent instructions | 导航与稳定协作约束变化 |
| PR 正文 | 候选、检查、合并、复盘及清理事实变化；更新后读回 |
| 原始验证报告 | 每次运行生成独立证据，历史报告不回写成新结果 |

每次收尾检查相关文件，记录更新位置、不适用原因、核实版本和未决项，不要求每次改动全部文档。可确定检查的缺字段 / 引用 / 状态冲突由工具处理，任意语义真伪由 Review 对照权威事实核对。

严格区分本地实现完成、远端交付完成和整个工作项完成。没有发布授权的本地目标可以准确结束本地范围，但不能宣称已发布；若整个目标包括交付，则保持生命周期未完成。合并后需要仓库文档修正时按项目 PR 规则交付；不直接在 master 补写，不为每个文档收尾制造无限循环的同类更新。

### 6. 接入与恢复

新项目仅在显式初始化后，发现已有 Agent instructions、技术栈、命令、验证入口、CI、文档职责与托管平台，准备适用配置及差异。未知技术栈不生成虚构测试或空壳绿色 job；没有 GitHub 访问时区分本地已准备与远端未验证。

已有项目复用既有机制，先展示冲突和 Diff；不覆盖用户修改，不自动放宽规则，不凭缺某文件认定项目未接入。远端配置先展示目标、检查来源、规则、权限和变化，取得明确授权后应用、读回并核对实际生效结果；失败或权限不足不能报告成功或扩大权限。

日常行为变化维护适用测试 / CI，不重复初始化。提供只读接入检查以识别工作流、远端规则及实际运行的偏差。

新会话、工具中断、linked worktree 或换机器后，用稳定工作项 / 仓库身份发现主记录、候选、用户改动、最近证据、预算和授权；与 Git / PR 冲突时核实相应权威事实。记录缺失不能推断完成，恢复写入前保留损坏原件或未知项。

### 7. Harness 持续维护

每次适用交付简短复盘；重复问题、重大故障、工具 / 工作流变化触发针对性复核。阶段性全面审计不变成每次小任务的固定成本。

缺口区分：规则缺失、已有规则未执行、工具缺陷、证据不足及产品实现问题；必要时同时记录产品与 Harness 问题。行动项复用已有工作项，列明责任、范围、验收、授权、暂缓原因、关联证据及复查条件，不因登记就认定已解决。

改进须证明原问题能被发现 / 阻止或所需事实能被准确恢复；优先确定性测试、检查或 Contract，不默认增加 Skill / 审批。Harness 自身改动也需要 Diff、Review、验证；不能为自己降低要求。

跟踪可获得的诊断无进展耗时、返工、状态冲突、人工纠正、恢复结果及检查耗时，未知不造值；第一版不设置未经测量的收益比例或复杂评分系统。删除 / 合并规则前说明独有保障如何保留、引用如何修复、历史在哪里；临时例外保留理由与复查触发条件。

### 8. 隐私与证据保留

通用工具默认不调用 LLM，不上传项目数据，不记录 Secret；说明和报告使用安全摘要、身份和引用，不自动展开 .env 或完整配置。真实服务、模型、付费调用和破坏性实验另按已确认授权执行。

清理候选 / worktree / 本地报告前核对唯一证据及已决定的保留位置；不能一边删除唯一证据，一边宣称仍可检查。原始证据无法恢复时如实注明，不补造。无需把敏感原始报告纳入 Git；保留安全的身份、摘要、位置和适用边界。

## Implementation Decisions 与职责边界

- ChatBI 保存本目标主 Spec、长期计划和总体授权；Plugin 仓库的关联记录仅保存其本地交付并指向主记录，不复制扩大授权。
- 通用状态 Contract、转换校验、预算、改动说明、初始化与维护行为归 Plugin；ChatBI adapter 拥有项目命令、文档清单、领域风险、CI / 远端检查及兼容入口。
- 使用现有文件 / Git 机制，不建设常驻服务、数据库或 Web 界面；工具不得要求付费模型才能进行状态检查。
- 工具打包 / 分发、状态字段版本、通用命令名、具体 adapter 文件布局、只读查询与写操作分离、稳定序列化及错误码等局部实现设计由 Design Review / Tickets 收敛，必须符合上述可观察行为，不提前指定新依赖。
- 实施前核实两仓库分支 / worktree、规则及用户修改，分别建立安全候选；不能在当前含用户归档的 Plugin 源目录直接混入目标写入。
- 安装 / 源版本 / 当前会话加载状态分别核实；走受支持同步路径，不手改缓存，不声称仅因源文件更新就已在会话中生效。

## Testing Decisions 与验收

设计审查的最小修订及具体实现约束见[设计说明](design.md)与[审查记录](design-review.md)。修订限定单一权威文件、证据来源分类、预算时间计算及现有容器兼容，不新增用户决定、依赖或外部服务。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 有效任务生命周期 | 能查询真实状态；满足依据时推进；本地、交付、总体完成不混淆 |
| 无证据 / 无授权转换 | 非零拒绝、原因可读、原记录不变，未知不当通过 |
| 记录冲突 / 中断 / linked worktree | 发现正确主记录和用户改动；冲突不覆盖；恢复预算和下一步 |
| 正常切片与越界改动 | 展示本轮 / 累计 Diff；正常继续；关键变化等待决定 |
| 诊断预算 | 使用可控时钟 / 合成事件证明第3轮或30分钟触发，重复命令与改名不能清零 |
| 正常等待与工具超时 | 等待单独记录，超时 / 未知不冒充进展或完整成功 |
| 源码 / base / 输入变化 | 相关旧证据失效或明确复用边界；旧候选批准不冒充新候选批准 |
| 动态文件收尾 | 缺项可被识别；适用文件更新，不适用有理由；历史不回写；远端正文读回 |
| 新 / 既有项目接入 | 从真实项目生成适配；保留用户修改；权限不足 / 无访问明确未完成 |
| 严格base规则 | 在获授权的无Secret隔离实验中，base移动后旧检查不能直接放行；失败 / 取消 / skip分别核对 |
| Harness 缺口与退出 | 现有规则执行偏差不靠重复规则解决；follow-up有证据；删除机制保留独有覆盖 |
| 隐私与旧状态兼容 | 不读取 / 输出真实Secret；旧记录不批量改写，旧完成不补造新证据 |
| ChatBI 端到端适配 | 用可复现合成工作项完成查看、拒绝转换、诊断升级、Diff、接入核验、恢复与收尾 |

测试优先使用临时 Git 仓库、合成状态 / Diff、可控时间和模拟远端返回，不运行真实付费模型，不对实际主分支注入失败。Mock 证明软件行为，不等于远端生效；真实远端规则和阻断验证必须单列授权、版本和实际结果。上述实验方案须先形成可审查计划再申请所需授权。

## Compatibility / Migration

现有长期文档和 Git 公共目录记录保留；新版字段 / 工具读取旧记录时区分可识别、需要核实和不适用，不从缺字段推出旧任务重新打开或已满足新门禁。只按当前目标需要迁移，不批量补造历史授权、复盘或测试结果。

既有命令和项目入口在适用时保留 adapter / 兼容入口，避免同时维护两套互相冲突的状态真相。迁移 / 弃用计划须列调用方、替代覆盖和引用更新。工具回退不能丢失原证据或擅自清理工作；远端设置回退需保留原配置并另按授权执行，不自动降低保护。

## Documentation 与 Done When

交付时更新 Plugin 的阶段规则、初始化说明和通用工具文档；ChatBI 更新适用的 Agent instructions、工作项 / 交付 / 文档维护规则、Runbook 与模板，修正当时仍存在的过期事实。正式项目文档只存当前规则，工作过程与历史结果留在所属 .scratch。

每仓候选有可核对 Diff、适用验证及 Code Review；两仓交付、安装同步和远端配置各自报告真实状态。涉及 Roadmap 的完成事实更新与不适用理由都须核对，不将本草案自动添加为已获实施授权的路线承诺。

整个目标只有已授权范围的适用验收、文档、Review、交付 / 复盘及已决定清理均闭合后才能完成；未获授权的独立远端保护、历史根因、云端收件等保留非目标 / 未验证，不冒充完成。
