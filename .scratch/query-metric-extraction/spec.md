# 查询解析保留客户指标说法

状态：用户已在当前对话确认；已授权需求评估和整理，实施拆分与实施授权见后续确认，不代表发布授权。

## 问题与事实源

用户要求查询解析提取客户表达的业务内容，不提前把客户的指标说法改成规范指标名；已接受保留既有歧义澄清及现有检索映射的方向。

基线为 `a247096f07adad73a907672e1c4312fd3d9c79ff`。当前正式 Contract 仍要求解析阶段唯一匹配后输出规范名，需要在本目标确认、实施时修订：

- [架构](../../docs/architecture.md)规定模型输出为候选，程序认证业务语义及物理映射。
- [在线查询](../../docs/specs/online-query.md)要求 Query Understanding 使用指标名称及别名，唯一对应时输出规范名；单轮及多轮提示词均执行这条规则。
- [在线检索](../../docs/specs/online-retrieval.md)约束发布资产、候选范围和失败关闭。实际实现按每个请求指标分别检索，并只接受候选规范名或登记别名的唯一匹配；文档中“一次综合检索”等表述与实际代码及原实施 Ticket 不一致。
- [完整查询条件与恢复](../../docs/specs/query-restoration.md)要求认证后使用规范指标身份，历史及恢复依赖该身份稳定；当前排序和聚合筛选的解析提示词也要求提前输出规范名。
- 现有检索测试直接以“人民币销售额”作为输入并确认权威指标“人民币净销售额”，但该模拟检索证据不代替调整后的真实在线验收。

本目标重新评估并替代旧工作项 `query-metric-alias-prompt` 中“解析输出规范指标名”的决定，不改变业务指标定义。

## 解决方案与边界

保持一条查询主链：原始问题 → 查询解析候选 → 结构校验 → 现有检索及权威指标认证 → SQL 候选 → 确定性校验 → 只读执行。

### 查询解析

1. 单轮、普通多轮 delta、网页历史首轮及历史多轮的新增指标说法，均保留客户当前表达中的指标词组，不用规范名替换别名。例如“人民币销售额”仍为“人民币销售额”，“毛利”仍为“毛利”。未修改的历史槽位仍按现有继承规则处理，不把继承状态伪称本轮原话。
2. 提取指标词组，不把主体、维度、普通行筛选或整句一起放进指标名；决定指标口径的修饰词继续保留。例如不能把“已完成订单数量”静默压缩为“订单数量”。
3. 指标词汇可继续给模型提供歧义判断依据，仅包含已批准的名称及别名；不因此授权模型改写输出指标说法或选择物理资源。
4. 保留现有澄清规则：“利润”等无法唯一确认的业务说法、无法确认含义的新说法返回受控澄清，不猜测为某个相近指标。超出支持范围、结构错误、Provider 故障维持原有不同结果。
5. 保留查询类型、时间粒度、筛选操作符等必要结构化判断及时间范围的程序标准化；这不是要求所有 JSON 值逐字复制。
6. 排序和聚合后筛选中的新指标引用也应与提取的指标说法一致，不通过其他候选字段绕过“禁止提前改规范名”。唯一指代可引用本次已提取或继承的指标；不能唯一指代仍澄清。

### 检索与认证

1. 保留现有向量检索、阈值、Top-K、同版本资产和候选范围；本次不增加候选选择 LLM。
2. 指标检索消费解析保留的说法；程序从本次检索到的权威候选中按登记名称或别名确认唯一指标。不能仅依据相似分数或排名第一就认定客户想要该指标。
3. 名称、公式、固定条件、数据来源及时间口径继续以权威发布事实为准，不改写或自动新增指标、别名、公式。
4. 生成 SQL 和成功历史状态前，由已有认证边界将指标及其排序、聚合筛选引用一致转换为认证的规范身份。局部代码如何复用认证结果留给设计阶段；不能建立另一份别名真相。
5. 解析阶段澄清时不进入检索、SQL 或数据库。若解析未拦截、检索后仍不能唯一认证，保留现有受控失败关闭，不让 SQL 大模型猜选；本次不新增检索阶段的交互澄清协议。

### 历史与兼容

认证成功后持久化的历史仍使用规范业务身份及既有状态版本；已保存历史、原结果和旧相对时间不重写。旧规范名与新输入别名都可通过同一权威事实认证。续聊失败或澄清不推进最后成功状态。

“换成同一指标的另一种登记说法”应按认证后的身份判断，不能因字符串不同导致排序悬空、错误丢弃既有聚合条件或误判指标变化；真正更换指标仍遵守旧排序继承和聚合条件澄清规则。

## 用户场景与可观察行为

| 输入或场景 | 解析候选 | 检索 / 认证及后续 |
| --- | --- | --- |
| 当前已完成订单的人民币销售额是多少？ | `metrics=["人民币销售额"]`，当前不作为日期过滤 | 认证为人民币净销售额，使用权威公式执行 |
| 已完成订单的营收是多少？ | `metrics=["营收"]` | 登记别名唯一匹配时认证为人民币净销售额 |
| 按产品线统计毛利和毛利率 | `metrics=["毛利", "毛利率"]` | 分别认证人民币毛利、毛利率，不能混淆或漏项 |
| 帮我查一下利润 | 受控澄清结果 | 不调用检索、SQL 或数据库 |
| 追问：把指标改成毛利 | delta 保留“毛利” | 合并及认证成功后使用人民币毛利；成功才更新状态 |
| 按销售额降序看前十个产品 | 指标和排序中的指标引用保持一致，保留客户的“销售额” | 认证为同一规范指标后生成排名条件并严格校验 SQL |
| 只保留销售额超过 50000 元的分组 | 聚合指标引用保留客户说法 | 按同一权威指标认证，保持聚合条件位置和数值含义 |
| 从旧历史续聊，改用同一指标的另一登记别名 | 新表达保留原话，旧槽位按规则继承 | 比较认证身份，保持语义一致的排序、筛选与可恢复状态 |

上述表描述指标相关片段，不要求候选只有 `metrics` 字段；既有完整结构仍必须满足。

## 实施决定与不变量

- 改变的是解析候选中指标说法的值语义及其下游引用衔接，不新增公共字段、不直接改变 HTTP 请求 / 响应结构。
- 不更换 LLM、Embedding、Qdrant、数据库或 SQL 解析库，不重建新查询流水线。
- 最多 5 个指标、所有请求指标完整覆盖、指标兼容性、认证 Join、SQL Guard、权限和只读边界保持。
- 原始问题是理解输入，不能在认证失败时用原始问题或模型 SQL 反向定义指标及条件。
- 本次不扩展经营分析产品行为；仅验证其复用查询执行边界不受影响。
- 旧规范名不禁止使用：客户本来就说规范名时，提取后仍是该规范名。

## 验收与验证

### 确定性软件验证

验证单轮及多轮提示词、候选结构和后续认证边界。重点覆盖登记别名的提取结果能进入现有检索，指标及排序 / 聚合引用在认证后保持一致、旧历史兼容、同指标不同别名的修订、真正指标变化的既有澄清边界，以及失败时下游不执行和状态不更新。

不能仅断言提示词包含某句文字来证明模型提取正确；模型行为由真实 Evaluation 另行提供证据。

### AI Evaluation

- 查询理解评测以客户实际说法作为期望，覆盖现有 6 条案例及毛利别名、多个指标、歧义澄清、明确规范名和多轮 delta；不能为符合模型实际规范化输出而改期望。
- 真实单轮及多轮走正式链路，确认原话输入检索后仍认证到正确指标并产生正确结果。
- 排序 / Top-N、既有合法聚合后筛选及历史续聊使用正式网页历史 profile 验证，不能只跑旧六字段评测代替。
- 报告绑定候选提交、案例及资源身份；明确区分“提取正确”“检索认证正确”“SQL / 最终结果正确”。
- 根据改动范围运行适用软件及文档检查；只在新失败或未解决风险需要时扩大验证，不把测试套件整理混入本目标。

### 交付条件

适用验证、只读实现 Review 和 Diff 检查完成；正式文档准确描述新候选语义及认证边界，不留相互矛盾的规范化要求。尚未运行的验证必须如实报告。
