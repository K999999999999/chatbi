# Harness 工作流控制与交付闭环

Spec Status: confirmed / 用户已确认
Last updated: 2026-10-01
Owner: 用户负责关键决定；当前主 Agent 负责整理、执行与交付。

## Problem Statement

现有 Harness 已有需求、Spec、Ticket、Review、CI 和 PR 规则，但规则之间存在衔接缺口：PR 检查后无人继续负责、实时状态被提交到 Git 后难以更新和清理、阶段之间重复等待确认，以及技术决策边界不够明确。用户需要掌握变化的目标、范围、功能链路、Contract 和关键技术选择，同时让 Agent 在已授权范围内持续完成工作。

本次审查观察到 ChatBI PR #37 和外置 Plugin PR #1 已合并，旧 `.scratch/harness-session-flow/status.md` 仍记录 PR 检查中，ChatBI PR 的复盘栏仍记为尚未执行。现有记录不足以完整还原上一次会话为何停止，不能将中断原因断言为用户漏看提醒。

审查快照同时确认：ChatBI `master` 有 active Ruleset，要求 8 项 CI，审批人数为 0；传统 Branch Protection API 的 404 不代表没有保护。Plugin 源与当前缓存一致。远端策略、安装与启用状态在实施和交付前应重新核实。

## Solution

围绕同一个工作目标，建立明确的关键决定、持续授权、本机状态和交付完成条件。长期事实源与实时进度分别保存；Agent 在授权范围内负责实施、验证、PR 跟进、复盘和安全清理，关键变化由用户决定。

本 Spec 固化会话中已确认的 15 项需求。用户已确认完整 Spec 和技术落实方案；该确认不代表现有仓库规则或本机配置已经改变，也不自动授权实施或发布。

## Change Profile

- Lifetime：长期维护的项目 Harness 与通用 workflow Plugin 约定。
- Size：跨仓库、多阶段；采用完整 Spec 和依赖明确的 Tickets。
- Risk：授权被误解、未完成交付丢失、错误清理用户工作、状态与验证证据不一致。
- Evidence：规则一致性检查、状态记录检查、可重复场景模拟和适用的新会话验收。
- Delivery：ChatBI 仓库与外置 `engineering-workflow` Plugin 分别遵守各自 Git / PR 规则；本机 Plugin 同步遵循支持的更新方式。
- Runtime：不改变 ChatBI 产品行为、业务 Contract、数据库或生产部署。

## User Stories

- 作为用户，我在实施前能够看到并决定业务行为、功能链路、Contract 和重要技术取舍，而不是事后接受既成实现。
- 作为用户，我授权整个目标后，Agent 能连续完成 Tickets 和交付，不需要我反复点击继续或去 GitHub 找待办。
- 作为后续 Agent，我能够从项目长期记录和本机共享进度恢复工作，即使 checkout 已回到 master 或原会话已中断。
- 作为用户，我的小改动也有长期记录，并且我的既有修改和无关工作始终得到保留。

## Scope / Canonical Source

### In Scope

- ChatBI 的 AGENTS、Harness 说明、本地工作项规则、Git / PR 工作流和 PR 模板。
- 工程阶段的技术澄清、确认、授权延续、验证复用、正式文档同步、PR 监控与安全收尾。
- 外置 `engineering-workflow` Plugin 中受影响的阶段 Skills、路由、初始化规则、README 和调用元数据。
- 共享本机状态的存储约定、字段、恢复、生命周期及旧记录的按需迁移。
- 自动合并的依赖控制约定及必要的 workflow 一致性调整。
- 流程验收记录，以及源文件校验后通过支持方式同步本机 Plugin 并验证加载。

### Source of Truth

- 本 Spec：当前目标的已确认需求、范围和拟落实的流程 Contract。
- ChatBI 的 AGENTS 与 docs/agents：实施完成后的项目稳定规则。
- docs/specs、docs/designs、docs/acceptance 等：各自承担正式行为、设计和验收职责，不由本机进度替代。
- 外置 Plugin 源：通用 Skills 的维护位置；安装缓存是派生产物。
- GitHub 实际 PR、Rulesets、CI 状态：远端交付事实，不能仅靠本机文本宣称。
- 本机共享记录：当前执行进度和恢复入口，不定义业务真相，也不扩大授权。

## Observable Behavior / Workflow Contract

### 1. 需求与技术方案澄清

先读取相关现状和权威事实源，再逐项澄清。事实能查明时不让用户代查；每轮只问最影响结果的一个问题。

澄清覆盖目标、用户与场景、正常和失败行为、范围、功能链路、输入输出及错误 Contract、状态和兼容性、模块职责与依赖方向、技术及依赖选择、数据和安全、验证、迁移与交付。每项给出明确决定，或者有证据的“不适用”。

关键方案应给出已有实现情况、推荐方案、适用的替代方案和取舍。只有关键决定已解决，才可宣布澄清完成。局部命名、函数内部组织等不改变已确认方案的选择可留给实施。

需要改变目标、范围、可观察行为、Contract、功能链路、关键技术、模块边界、依赖方向或重要安全 / 状态决定时，先报告原因、影响和方案，取得确认并更新记录，再修改相关实现。不得以 CI 修复、重构或小改动为由绕过这一边界。

只读查证不足时进入经确认的小实验。实验记录问题、范围、文件与副作用、判断标准和结果；未经正式方案确认和适用验证，不将实验实现直接作为正式交付。

### 2. 规划与授权

复杂目标经过完整 Spec 确认、设计审查、Ticket 草案、当前上下文的 Readiness 和拆分确认。技术审查与 Readiness 可由 Agent 在已授权目标内执行，不要求用户逐个调用 Skill。

Ticket 拆分确认与整体实施授权是不同事实；若用户已明确要求完成整个目标，就记录整体授权并按依赖执行全部 Tickets。若用户只授权某个 Ticket，则只执行该范围。

设计审查为 PASS WITH MINOR FIXES 时，先逐项修订并留下核对结果，再交接。修订改变用户决定时重新确认；不改变决定的修订自行处理并报告。

小改动先在 `.scratch/<work-item>/spec.md` 保存目标、范围、预期结果、验收与验证方式，以及用户明确指令的授权依据，再实施。不机械新增 Tickets、设计审查或行为代码 TDD；行为变化仍需适用测试。存在关键歧义或重要边界变化时升级到澄清和完整流程。

实施授权不自动等于发布授权。发布前报告目标、提交范围、风险、验证证据，以及默认自动合并行为。取得发布授权后，同一目标、同一范围内的 Push、PR 更新、CI 修复、复盘记录和安全清理持续有效，不逐次询问。

授权绑定工作项目标与范围，而不是凭其他工作项、旧 PR、插件安装或本机记录推断。用户限制某次动作或撤销授权时立即按新限制执行。

### 3. 记录与恢复

长期规划保存在 `.scratch`；正式项目事实更新至对应 docs 和验证入口。实时状态从 Git 跟踪中分离，并由同一仓库的 worktree 共用。

新会话先检查实时 Git 和共享记录。实施恢复按工作项 ID、branch、worktree 和关联范围匹配；交付恢复按仓库与 PR 身份核验。位于 master、远端 head 已被删除或 Feature worktree 已清理，都不使可识别的未完成交付消失。

已授权且明确归属的未完成任务可以继续跟踪和安全收尾。出现工作冲突、归属不明、未知授权或用户改动阻碍清理时，报告具体原因与最关键的待决定问题。无活动工作时正常处理当前请求，不要求用户选择历史记录。

记录更新发生在阶段变化、重要决定、验证、Ticket 交接、PR 发布和状态变化、真实阻塞、会话交接及完成时。记录必须包含唯一可执行的下一步；普通 CI 运行属于推进中的等待，不宣称失败或完成。

换机器或本机状态丢失时，依据已提交记录和远端事实重建进度。无法核实的授权和归属明确标为未知，不自动进行破坏性清理或新的远端写入。

### 4. 验证与实现完成

每份验证证据记录命令或场景、对应提交 / 尚未提交的变更范围、适用基线、覆盖行为、结果和未覆盖范围。再次修改后判断证据是否仍适用；没有影响的行为可复用，影响范围不明则扩大检查。远端 required checks 必须对应实际待合并版本。

测试、AI Evaluation、业务验收和运行时证据各自证明相应行为。代码未变化时不为进入下一个阶段而重复同一验证；相关行为、依赖、基线或验证环境变化时重跑受影响检查。

实施完成要求 Contract 和 Done When 满足、适用验证有结果、代码 Review 与 Diff 检查完成、受影响正式事实源同步。记录同步位置或不适用理由。实施完成不代表 PR 已合并或整个交付已完成。

### 5. PR 跟进与依赖

发布授权默认允许普通 PR 在必需检查通过后自动合并，不新增用户 PR Review。Agent 不直接执行人工 Merge，遵循目标仓库真实自动化和保护规则。

独立 PR 可走默认自动合并。依赖 PR 必须记录前置 PR、最终 base 和交付顺序；前置未合并、base 错误或适用检查未通过时不得启用自动合并。先保持 Draft，再核对条件后转为 Ready。同步后的检查须对应实际待交付版本。切换 base 后不得仅复用旧绿色状态；应核对 head、验证基线和覆盖范围，通过目标仓库已有 CI 触发方式取得适用证据后再转 Ready。

发布后立即记录远端身份和提交版本，持续核实 CI 与真实 PR 状态，处理范围内问题。正常等待不能因为达到两分钟而成为结束理由。确有需要用户决定的事项、外部阻塞、用户中断或会话无法继续时，先保存已知状态、阻塞原因、下一步，并在聊天里交接。

Agent 无法保证会话关闭后继续运行；本次以新会话恢复作为保障，不承诺不存在的后台唤醒机制。PR 说明里的待办不替代聊天交接和共享记录。

PR 已关闭但未合并时保留可能有价值的分支，说明状态；CI 失败先诊断，范围内修复继续，涉及关键决定时返回确认。

### 6. 合并后复盘与安全清理

核实合并后记录 merge commit、远端检查和交付结果，完成简短 Harness 复盘。无新增缺口明确记录；有缺口给出表现、证据、原因和最小改进建议，在 PR 和聊天中报告。

范围内问题继续处理；范围外 Harness、全局 Skill 或规则改进只建立独立的规划记录和建议，不自动实施或创建未授权的外部 Issue。必要时为产品缺陷与 Harness 缺口分别建目标。

安全清理逐项核实唯一归属、已合并、干净 worktree、没有用户未推送工作、没有合并后新增工作、没有依赖以及非 master / protected / backup 目标。同步主干，按目标仓库策略清理本次唯一 Feature worktree / branch 和远端 head，并重新核实结果。

用户改动或依赖阻碍清理时仍完成可执行的复盘，记录哪些步骤已完成、清理为何阻塞和下一步；不覆盖改动，也不把阻塞任务标为全部完成。最终结果、验证、复盘和剩余事项在聊天里汇报。

## Implementation Decisions（已确认的技术落实方案）

### 本机共享状态

- 采用现有 Markdown 和 Git 工具，不新增数据库、状态服务、队列或后台守护进程。
- 通过 `git rev-parse --path-format=absolute --git-common-dir` 解析当前仓库的公共 Git 目录；建议状态位置为 `<git-common-dir>/harness/work-items/<work-item-id>/status.md`。
- 不假设 worktree 根目录的 `.git` 是目录，不手工修改 Git 的 HEAD、index、refs 等内部文件。
- 工作项 ID 独立于 branch；记录 branch 和 worktree 只是关联，不是生命周期主键。
- 跨仓库目标在各自公共目录建立关联记录，使用同一目标 ID，指向主 Spec，并列出各仓库交付。主目标只有所有适用交付与收尾完成后才 done。
- 主仓库记录是目标授权与总体阶段的权威位置；关联记录保存本仓库交付与主记录引用，不复制出第二份可独立扩张的授权。主记录不可用时先核实长期依据，不推定新的远端写入或清理授权。
- 状态采用明确字段：ID、Status、Stage、Owner、Spec 路径、Repositories、Branches、Worktrees、已确认决定引用、实施 / 发布 / 实验授权范围与依据、PR 身份、验证引用、最后检查与更新时间、阻塞原因、上次停点和下一步。
- Spec、Ticket 和验收证据引用包含仓库身份、仓库相对路径与适用提交；绝对 worktree 路径仅作当前位置。未提交的规划文件仍在 worktree 中时不得删除该 worktree。
- 同一目标更新状态时只有一个写入 Owner。写入前重读并核对记录版本 / 更新时间；发现另一写入者或新更新时暂停覆盖，按事实解决归属。使用现有文件操作完整保存后再替换，避免半写记录。损坏、缺字段或归属无法核实时保留原记录并恢复事实，不依据错误记录扩大授权。
- 清理仅删除目标 Feature worktree / branch，不删除公共目录中的恢复记录。已完成记录保留并标为 done。
- 长期验收证据在合并前随项目提交；合并后实际结果和复盘保存在远端 PR，本机记录保存引用，聊天给出完整交付报告，避免为更新实时阶段追加 PR。

### 生命周期

- 保留 Status 的 open / in-progress / blocked / done；Stage 描述实际阶段。
- 明确需求发现、需求与技术澄清、方案实验、Spec 待确认、设计审查、Ticket 待确认、实施、验证 / Review、待发布授权、PR 跟进、已合并待复盘、待清理、完成等阶段。
- 正常 CI 等待维持 in-progress；确有不能继续的阻塞记录 blocked 与恢复条件。
- 实施完成、PR 合并、复盘完成、清理完成分别记录，不用其中一个代替整项目 done。
- 适用交付已合并、复盘与证据已留存、安全清理完成或由用户明确决定保留后，才可报告整个目标完成。用户明确保留分支属于已决定的结果，不伪称已删除。

### Skill 与项目规则

- 项目入口仍由 AGENTS 驱动；阶段 Skills 在上下文与授权满足时可由 Agent 使用，不要求用户逐个手动调用。
- 拟允许需求发现、澄清、Spec、设计审查、Ticket、Readiness、实施、TDD、代码 Review 和交付等阶段 Skills 被按任务调用，并同步其正文与调用元数据。允许调用不等于允许越过确认门禁。
- `ask-matt` 保持可选导航；setup 和 Wayfinder 保留需要明确启动的边界；小实验仍需要独立确认。
- 通用 Plugin 不将 ChatBI 的存储路径或默认自动合并策略强加给其他项目；先读取并遵循目标项目规则。
- 源验证通过后，通过 Codex 支持的方式更新安装并核实源 / 缓存与新会话加载；不手工改安装缓存。
- 同步前核实 marketplace 实际指向的源目录和 checkout，避免从旧源更新缓存；当前 Thread 不视为已热更新。清理 worktree 不能破坏仍在使用的安装来源。

### 自动合并与监控

- 使用现有 GitHub Actions、Rulesets、Git 和 gh；不引入 Provider SDK 或自动人工 Merge。
- 发布前说明真实自动合并行为；同步修正 delivery Skill 里说明晚于 PR 创建的顺序。
- 依赖交付通过 Draft 与明确的依赖记录保护；转 Ready 前核实前置、最终 base 和适用检查。相关 workflow 不得与这一约定冲突。
- Auto-merge 动作读取实时 PR 的 Draft、head 和 base，不只依赖可能过期的事件快照；发现状态变化先退出或重新检查，不启用已不满足条件的交付。
- 默认周期性检查可沿用两分钟量级，优先用可用的事件 / monitor 机制；每次阻塞等待不超过产品限制，并持续给出有意义的进展。间隔是工具策略，不是责任期限。
- 远端配置不足、检查不可核实或依赖不明时不擅自关闭保护或启用自动合并；先报告并处理所需决定。

## Compatibility / Migration

- 保留现有长期 Spec、Ticket、决策和验收记录，不批量迁移目录或改写已完成历史。
- 旧 `.scratch/<feature>/status.md` 作为历史快照；恢复旧活动任务时核实 Git、PR、用户改动和授权，再按需导入共享本机记录并建立来源引用。旧快照不继续作为实时权威状态。
- 本次工作在新规则实施前使用现有 `.scratch/<feature>/status.md` 记录规划阶段；新机制就绪后迁移当前工作，不继续通过 tracked status 维护交付状态。
- 现存其他 worktree 的用户改动保留；本项不顺带清理旧分支。跨仓库修改分别遵守各仓库规则。
- 若新机制无法安全恢复，保留文件并报告具体缺失；回滚只针对本项新增规则和实现，不能通过清理用户工作恢复。

## Testing Decisions / Acceptance Criteria

采用可重复模拟、必要的真实 Git / PR / 新会话场景和文档一致性检查。每个场景留存输入状态、已授权范围、执行动作、可观察结果和实际证据，不用仅阅读规则替代流程验证。

记录明确标记模拟 fixture 与真实执行结果。共享状态场景使用隔离 Git 仓库和 worktree；授权边界场景观察拒绝写入的实际动作；新会话场景验证实际加载和恢复行为。模拟检查通过不表述为真实 PR、真实 CI 或后台唤醒已验证。

| 场景 | 必须观察到的结果 |
| --- | --- |
| S01 发布后两分钟 CI 仍运行 | 保持跟进，记录进度，不因时间到而结束交付。 |
| S02 最后检查后 PR 合并，原会话中断 | 新会话核实远端并恢复复盘 / 清理，在聊天里报告。 |
| S03 当前 master，原 head 或 worktree 已删除 | 通过工作项与 PR 身份恢复，未完成交付不丢失。 |
| S04 两个 worktree 读取和更新同一目标 | 共享记录可发现且不制造 Git 改动；归属和授权无歧义。 |
| S05 合并后更新状态 | 无需新增 Commit / PR，不因状态更新阻碍清理。 |
| S06 用户改动或其他依赖阻碍清理 | 保留改动和分支，复盘可完成，记录清理阻塞，不声称目标全部完成。 |
| S07 无活动工作或用户只读咨询 | 正常处理请求，不强制用户选择过期记录或创建实施 Spec。 |
| S08 整体实施与发布已授权 | 按依赖连续推进；范围内 CI 修复与 PR 更新不重复确认。 |
| S09 技术方案、Contract 或范围需要变化 | 修改相关实现前报告影响、取得新确认并更新依据。 |
| S10 明确的小改动 | 先在 .scratch 保存短 Spec，再直接实施并留存验证；无重复短 Spec 确认。 |
| S11 设计审查需要小修 | 修订项落实并核对；改变关键决定时重新确认。 |
| S12 验证后仅无关文档变化 / 相关行为变化 | 前者复用仍适用的行为证据；后者重跑受影响检查，PR CI 对应待合并版本。 |
| S13 依赖 PR 不满足条件 / 条件已满足 | 前者不自动合并；后者核实前置、base 与检查后才转 Ready。 |
| S14 只读查证不足，提出小实验 | 未确认前不执行；确认后按边界留存结果，正式方案另行确认。 |
| S15 复盘发现范围外缺口 | 留下证据与独立建议并在聊天汇报，不自动扩大实施范围。 |
| S16 正式文档同步与最终报告 | 指明更新位置或不适用理由；交付报告区分实施、合并、复盘与清理结果。 |
| S17 新机器无本机状态 / 旧记录过期 | 从长期事实和远端核实恢复；无法核实的授权不自动推定。 |
| S18 Plugin 源、缓存与新会话 | 支持方式同步，源 / 缓存一致，按阶段加载且不越过用户确认门禁。 |
| S19 共享记录存在更新冲突、损坏或缺字段 | 保留原记录，不覆盖其他写入者，不从错误记录推定授权；明确恢复条件。 |
| S20 跨仓库关联记录或临时路径失效 | 主目标授权仍只有一个权威来源，依据稳定引用核实；不能将单个仓库完成当作全部完成。 |

纯规划和规则文档不运行 ChatBI 产品测试；若修改可执行逻辑，按实际风险补充对应确定性验证。真实远端写入、实验和发布仍遵循授权边界，不为验收自动操作用户的旧 PR。

## Out of Scope

- ChatBI 产品功能、业务 Contract、查询链路或生产配置变化。
- 修改 `agent-engineering-skills` 等无关 Plugin。
- 新建后台服务、跨机器实时同步、自动恢复用户关闭后的 Agent 进程。
- 自动部署、关闭 CI 保护、绕过 required checks、直接人工 Merge。
- 未经授权执行小实验、范围外 Harness 修复、创建外部 Issue 或批量清理历史分支。
- 在本 Spec 确认前实施上述规则；Spec 确认不等于尚未授予的发布授权。
