# 文档迁移与维护门禁设计

Status: 已确认 Spec 内的实施细化，随设计审查核对；不扩大产品行为或远端授权。
事实源：[Spec](spec.md)、[处置清单](file-plan.md)，规划基线 `c7f7e74`。

## 迁移依据与内容保全

所有原文均可从规划基线读取；本目标使用 `.scratch/current-documentation/migration-ledger.md` 记录逐批迁移结果，不建立新的正式文档注册表或全局配置。

每个被整理的来源至少记录：原位置与规划基线、当前规则的目标文档 / 章节、独有历史内容的保存位置或已有完整覆盖证据、被移除章节的处置理由、引用修复与 Review 结果。历史文件只修复路径与必要锚点，不改候选、环境、原结论和授权历史。

按章节或规则核对，不能只凭文件名认定“已覆盖”。当前 Spec 中重要的输入输出、失败状态、授权 / 安全、数据归属、资源限制和兼容边界必须能指向当前文档。当前实现核对以代码和测试为证据，已确认 Contract 的语义优先。

正文改写顺序为：核对来源 → 保存独有证据 → 提供当前内容 → 修复所有消费者 → 检查 → 移除冗余旧入口。每个 Ticket 完成时全库链接可用；不通过统一重定向掩盖旧锚点含义不同的问题。

归档优先放所属 `.scratch/<work-item>/history/`，无所属目录者放本工作项 `history/` 并保留原来源信息。对应工作记录已有完整内容时无需复制原稿，但必须记录覆盖依据。删除独立入口前发现不能确认覆盖的内容时，保留原件并停止该条迁移。

只修复受迁移直接影响的历史记录引用；不把历史工作整体重写成当前状态。Git 公共目录中的本目标进度正常更新，其他记录仅在当前字段指向已移动事实源而影响恢复时修复路径并注明原因，不改变旧授权、PR 或结论。

## 本地与 CI 检查入口

沿用 `python -m scripts.check_markdown_links` 及 `--root`，保持原有链接检查行为与调用兼容。新增 `python -m scripts.check_documentation --root <repo>` 作为完整文档检查入口，组合现有链接检查与正式文档结构检查。

现有 CI 的 Deterministic tests job 使用完整入口替换原链接检查调用，模块边界步骤继续保留。不改 job 名称，不新增第三方包、工作流或远端设置。Runbook 与协作规范说明完整本地命令；旧链接入口作为专门检查仍可使用。

链接检查遍历现有 Git tracked / untracked 非 ignored Markdown，包括 `.scratch/`。结构检查在这一文件集合中，仅选择 README.md、AGENTS.md、已存在的 CONTEXT.md / CONTEXT-MAP.md 和 `docs/**/*.md`，不将仓库其他历史记录加入风格门禁。

缺少 Git 仓库或读取失败不能伪装成检查通过；命令应报告失败并非零退出。与现有工具相同，检查只读，不修复、不写文件、不运行文档中的命令。

## Markdown 解析与最小结构规则

共享已存在的围栏识别和行内代码过滤逻辑。可抽取一个小型 `scripts/markdown_content.py` 辅助模块，由链接和结构检查共同调用；模块只提供保留行号的正文迭代与代码过滤，不建立 AST、插件体系或通用 Markdown 框架。

围栏支持现有反引号与波浪号形式，闭合符号须与开始符号一致且长度不短于开始。被跳过行保留行号 / 空行边界，避免 Setext 标题跨越代码块误配。解析变动需通过已有链接回归，不能因新增结构检查损坏历史链接和锚点行为。

结构检查识别 ATX 标题以及现有锚点解析支持的 Setext 标题，使用原始行号定位。连续标题从较浅层跳到深两层或更多报错；回到任意较浅层合法。本轮不新增“强制所有文件存在唯一一级标题”等未确认规则。

正文章节符号后跟数字章节编号的引用报错，允许用反引号写出的说明性字面量、代码围栏中的示例和单独说明符号含义的文本。复用行内代码过滤避免误报。具体数字匹配及跨空白形式在测试中固定，说明性字面量用明确 Markdown 表达，不靠猜测中文句子判断例外。

输出包含文件相对路径、行号、规则名与可行动提示；正常退出 0，任何链接 / 结构错误非零退出。不用硬字数阈值、阶段词禁用或关键词推断语义。

## 有意义的回归证据

使用临时 Git fixture 验证文件发现、`--root` 和进程退出码；纯字符串用例验证围栏、行内代码、ATX / Setext 与行号。已有 `tests/scripts/test_check_markdown_links.py` 继续运行，新增文档检查测试放在同一脚本测试区域。

至少覆盖：

- 正确层级与具名链接成功；向下跳级失败，向上返回合法，代码示例里的标题不报错。
- 正文章节符号引用失败；行内代码和两类围栏的字面量成功；`.scratch/` 历史正文不触发结构规则。
- 已跟踪与新增未 ignored 正式文档均受检查；ignored 文件与历史目录不进入结构检查。
- 根目录与嵌套本地链接、失效目标 / 锚点、迁移后的历史相对链接均受链接检查。
- 同一 fixture 通过完整 CLI 与函数入口得到一致结果；缺少 Git 仓库不能输出成功。

CI 是否调用相同入口通过工作流内容和本地命令验证，最终发布时核对已有 required check 的真实远端状态。当前阶段不修改远端配置，也不宣称合并阻断已生效。

## 规则与语义核对

AGENTS.md 只保留稳定短规则和入口，详细维护规则集中在 `docs/agents/documentation.md`；任务恢复、授权和交付分别保留在 tracker / Git 工作流。原 Harness 说明中的有效要求逐项落位，独有演变理由归工作记录。

现有 PR 模板、Done When 与 Agent Review 增加对应文档核对记录，不新增人类审批环节。重复定义、历史混入、操作前提与可读性通过现有 Review 及阅读走查判断，明确这是门禁脚本的语义能力边界。

## 切片、失败处理与恢复

按四个读者可验证的闭环依次推进：当前行为事实 → 阅读入口与架构 / 实现说明 → 操作与历史证据 → 维护规则和完整门禁。每批内容提供、引用修复、链接检查和 Review 同时完成，后续批次不承担前一批断链修复。

门禁在正式文档重组完成后接入现有 CI，避免在合法迁移的中间状态让仓库检查必然失败。每个切片记录验证对应的候选 / 未提交范围，本目标最终保存完整迁移和语义核对证据。

失败处理：对内容覆盖不明或无权威依据的冲突，停止受影响条目的删除并保留来源；修复前不推进依赖该条目的切片。脚本误报先固定 fixture 再修复，不能以忽略全部 docs 绕过门禁。

本目标无运行资产或数据库迁移。授权范围内通过后续补偿提交恢复文档与工具；单批恢复须同时恢复原文、引用和 CI 调用。不得 reset 用户修改，已依赖的切片需要一并核对，回滚不删除历史唯一副本。

## 方案取舍

比较过把所有内容塞入架构 / README，及给每项功能强制保留完整 Spec / Design / Acceptance。前者使入口承担过多规则，后者延续重复维护与历史混入；选用按当前职责整理、按需保留机制、在工作记录保留过程的方案。

检查复用现有链接工具并增加一个轻量完整入口，避免修改所有旧调用和新建重型文档平台。新增共享解析仅服务两个实际消费者，并由现有回归保护。

Owner: 当前主 Agent；维护责任由后续实际修改者承接。若后续引入新的文档形式或门禁误报，需要在此项目规则内调整解析 / 范围，不通过新增不受检查的正式目录绕过约束。
