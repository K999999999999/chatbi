# 经营分析：双时期产品因素归因 V1

Status: confirmed

## Problem Statement

现有经营分析 V1 已能拆分和执行多任务，但当前 Golden Set 混有趋势、区域拆分、下钻和原因分析等目标，未覆盖用户要解决的核心问题：比较两个时期的毛利或销售额变化，定位主要产品贡献，并说明变化来自售价、销量或单位成本。

本 Spec 为经营分析的新目标范围。历史 `.scratch/business-analysis-v1/spec.md`、已完成 Ticket 和 `docs/acceptance/business-analysis-v1-20260921.md` 保留为旧版实现及验收记录，不覆盖、不改写。实现时以本 Spec 替换经营分析当前的行为范围，同时保留普通查询和现有安全边界。

## Solution

经营分析 V1 只支持一个场景：**两个时期之间的毛利或销售额变化归因**。

- 用户必须给出能唯一确定的两个比较时期。无法确定时先澄清，不执行查询。
- 支持的目标指标为毛利和人民币净销售额（用户口语中的销售额）。销售成本不是独立分析目标。
- 以产品为归因分组，报告整体变化、贡献最大的产品，以及这些产品内各因素的贡献金额和方向。
- 毛利变化拆为实际成交单价、销量、单位成本三个因素；销售额变化拆为实际成交单价、销量两个因素。
- 区域、客户、客户类型、产品线等不作为首轮自动分析维度。
- 每个查询任务通过现有 Natural Query / Online Query 正常链路执行；因素贡献由确定性计算产生，Summary LLM 只负责根据结果组织解释。

### 归因口径

每个产品、每个时期使用：

- 数量 `q`：已完成销售明细的 `quantity` 之和；
- 销售额 `r`：人民币净销售额之和；
- 成本 `c`：人民币销售成本之和；
- 实际成交单价 `p = r / q`；
- 单位成本 `u = c / q`。

单价使用人民币净销售额除以数量，包含折扣和汇率影响；不得直接跨订单比较多币种的 `unit_price_transaction`。

比较两个时期 0（较早）和 1（较晚）时，按对称分摊法计算交互影响：

- 销售额单价贡献：`(p1 - p0) × (q0 + q1) / 2`；
- 销售额销量贡献：`(q1 - q0) × (p0 + p1) / 2`；
- 毛利单价贡献：`(p1 - p0) × (q0 + q1) / 2`；
- 毛利销量贡献：`(q1 - q0) × ((p0 - u0 + p1 - u1) / 2)`；
- 毛利单位成本贡献：`-(u1 - u0) × (q0 + q1) / 2`。

各因素贡献相加必须等于对应产品的实际指标变化；所有产品贡献相加必须等于整体指标变化。成本下降对毛利是正贡献，成本上升对毛利是负贡献。

若产品只在一个时期有销量，该产品没有可比较的两期单价或单位成本。此时将其完整销售额或毛利变化单列为“新品进入 / 产品退出贡献”，不伪造缺失时期的单价、单位成本，也不将其硬分配到价格、销量或单位成本。其余两期均有销量的产品继续使用上述归因公式。所有产品类别及因素合计仍须对上整体变化。

报告按整体变化方向选择贡献最大的至多 3 个产品：整体上升时选择正向贡献最大的产品，整体下降时选择负向贡献最大的产品；产品更少时全部列出。总结必须先陈述查询得到的真实变化方向，不采信用户问题中与数据相反的预设。

### 输入、输出和边界行为

输入为用户自然语言问题。输出为自然语言经营分析报告，至少包含：

- 两个时期和目标指标；
- 整体指标的实际变化方向和金额；
- 贡献最大的产品及其因素贡献方向和金额；
- 产品新增或退出时对应的独立贡献；
- 查询失败或证据不足时的明确说明。

指标“利润”不能唯一确定为毛利时，先澄清口径；用户明确指定当前未支持的指标时，不生成虚构结果。报告不得把售价、销量或成本的相关变化写成查询结果无法支持的更深层经营原因。

## User Stories

- 作为业务用户，我可以比较两个时期的毛利，看到整体毛利变化由哪些产品贡献，以及这些产品的售价、销量和单位成本各影响多少。
- 作为业务用户，我可以比较两个时期的销售额，看到整体变化由哪些产品贡献，以及实际成交单价和销量分别影响多少。
- 当我没说明比较时期时，系统会先询问要比较哪两个时期，不自行猜测。
- 当我使用“利润”等无法唯一映射的指标说法时，系统会先询问指标口径，不自动当作毛利。
- 当问题中的上涨或下降前提与数据库事实不一致时，系统会纠正前提并按真实结果解释。

## Implementation Decisions

- 经营分析仍按单个问题独立分析，不读取或写入普通查询的 Multi-Turn 状态。LangGraph checkpoint 仅用于恢复同一次经营分析运行，不作为跨问题会话记忆。
- 用 LangGraph `StateGraph` 编排拆解、校验、查询、归因和总结节点；查询 Task 顺序执行。LLM 只识别目标指标和两个时期，程序校验后生成固定查询 Task，不允许模型增加区域、客户等分析维度。
- 任务查询复用现有 Natural Query / Online Query；授权、SQL Guard 和只读数据库边界不变。
- 每个查询 Task 独立调用一次 Natural Query。首版按两个时期分别查询整体指标及产品指标；毛利查询产品净销售额、已完成销售数量和销售成本，销售额查询产品净销售额和已完成销售数量。
- 数量、人民币净销售额和人民币销售成本来自已完成销售明细；实际成交单价、单位成本及归因金额由确定性程序计算，不交给 LLM 计算。
- 为让任务通过正常 Natural Query / Online Query Contract 查询数量，在指标目录增加“已完成销售数量”，口径为已完成销售明细的 `SUM(f.quantity)`，别名包含“销售数量”“销量”；只统计 `order_status = 'completed'`，时间按 `completion_date_key -> dim_date.full_date`。它成为普通自然查询可用的正式语义指标，不是经营分析私有字段。指标目录更新后按现有流程重建并发布 RAG 离线资产。
- Summary LLM 只消费已完成任务结果与确定性归因结果，不能更改数值、方向、产品排序或指标定义。
- 任一必需查询 Task 失败、结果截断或贡献对账失败时，不运行 Summary LLM 生成原因结论，直接返回未完成原因。
- 对网络、数据库暂时不可用和 LLM 服务暂时失败等可重试基础设施故障，当前 Task 自动重试一次；仍失败则保留 checkpoint，允许在有效期内恢复。澄清、授权失败和 SQL 校验失败不重试。
- `analysis_run_id` 由客户端在首次请求前生成，并作为 LangGraph `thread_id`。同一认证用户以相同 ID 和相同问题重试时，未完成运行从 checkpoint 恢复，已完成运行返回保存结果；同一 ID 用于不同问题或不同用户时拒绝。超过 24 小时后过期的 ID 不得自动启动新分析，用户必须生成新 ID。
- 每次 HTTP 请求仍使用独立的 `request_id` 和 `trace_id`；通过 Trace 属性关联 `analysis_run_id`，不复用这些 ID 作为 `thread_id`。
- 使用持久化 PostgreSQL Checkpointer，将 checkpoint 写入与销售业务库分离的 `chatbi_control` 专用表；销售业务库查询连接保持只读。运行创建时绑定认证用户，恢复时重新认证并检查归属；不持久化 AuthContext 或凭证。checkpoint 保留 24 小时并自动清理。
- 当前指标目录中的“人民币净销售额”和“人民币毛利”是业务指标事实；本 Feature 不增加“销售成本”作为独立原因分析目标，也不将原始多币种交易单价作为统一价格指标。
- 首轮不自动添加任何其他维度。用户明确提出区域等其他分析需求时，作为单独自然查询或后续需求处理，不纳入本场景的归因因素。

## Testing Decisions

### 五条 AI Evaluation 案例

| ID | 问题 | 预期行为 |
|---|---|---|
| BA01 | 保留原问法：“2025年3月毛利为什么比2月下降？” | 实际毛利上升约 18,195.32 元（约 20.03%）；系统纠正“下降”前提，按毛利的单价、销量、单位成本口径分析主要产品。不得为迎合原问法修改测试数据。 |
| BA02 | “2025年毛利为什么比2024年下降？” | 实际毛利下降约 25,889.56 元；按毛利三因素归因并解释主要负向产品贡献。成本下降须作为正向抵消贡献，不得说成成本上升。 |
| BA03 | “2025年3月销售额为什么比2月增加？” | 实际人民币净销售额增加约 38,673.15 元；按产品解释实际成交单价和销量贡献，不分析成本。 |
| BA04 | “最近毛利为什么下降？” | 比较时期不明确；先询问比较哪两个时期，不执行查询任务。 |
| BA05 | “2025年利润为什么比2024年下降？” | 时期明确但“利润”口径不明确；先澄清用户指的指标，不执行查询任务。 |

### 正确性判定

- 正常案例通过系统的自然语言入口运行，查询结果与独立 PostgreSQL 参考 SQL 的结果比较。
- 程序确定性检查指标、期间、产品结果、因素方向和金额，并验证每层贡献汇总能对上实际变化；显示值四舍五入后允许不超过人民币 0.02 元的累计显示误差。
- LLM Judge 检查最终总结是否正确描述实际变化方向、主要产品、因素方向和查询证据，是否存在编造或与数据矛盾；LLM Judge 不负责重算贡献金额。
- BA04 和 BA05 检查系统是否返回对应澄清结果，且澄清完成前没有执行查询任务。
- 确定性软件测试覆盖公式、正负方向、贡献对账、新品 / 退出产品处理和舍入边界；该类边界用固定数据测试，不额外增加 AI Golden Case 数量。

## Out of Scope

- 期间趋势、单期分组汇总、区域拆解、客户拆解、客户类型拆解和产品线拆解作为独立经营分析场景；这些属于 Natural Query 或未来明确的下钻能力。
- 首轮自动追加区域、客户或其他分析维度。
- 销售成本作为单独目标指标。
- 在现有可观察数据之外进一步推断定价策略、需求变化、采购原因或其他因果机制。
- 预测、模拟、预算规划、自动经营动作和经营建议执行。
- 修改普通查询、Multi-Turn、授权、RAG、SQL Guard 或数据库事实口径。
- 修改开发种子数据以迎合测试问题中的错误前提。

## Further Notes

- 事实源：`docs/architecture.md`、`docs/product-scope.md`、现有 Query API / Online Query Contract、`src/semantic/metrics.json`、销售事实表结构，以及当前 Business Analysis V1 代码和验收记录。
- 本地 PostgreSQL 只读核对确认：已完成销售明细存在数量、交易币种单价、人民币净销售额、人民币单位成本和人民币销售成本；交易币种包含 CNY、EUR、JPY、USD。数量将通过正式指标“已完成销售数量”由正常 Natural Query 查询；实际成交单价和单位成本由人民币金额与数量在经营分析内确定性计算，不新增独立单价 / 单位成本指标。
- 首版跨时期产品匹配沿用 Natural Query 返回的产品名称，暂假设比较期内名称稳定；若同一产品改名，不做实体识别，可能分别呈现为产品退出和产品进入。本 Feature 不增加产品 ID 专用查询通道。
