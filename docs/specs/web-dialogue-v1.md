# R1：电脑端 Web 对话与经营分析入口

当前 Web 长期状态以 [R3 History Spec](history-results-v1.md) 为准：显式 `/api/v1/histories` 与 `/api/v1/saved-results` 保存私人快照，刷新只读，续聊恢复完整条件；旧 `/api/v1/query` 继续原短期 Contract。本文保留 R1 的历史行为 Contract；R4 对历史页面增加独立的异步执行与状态观察路径，细节见已确认 [R4 Spec](../../.scratch/execution-streaming-v1/spec.md)。R1 原临时等待边界不代表当前网页执行生命周期。
状态：用户于 2026-10-03 整体确认；实现、旧入口移除和最终候选本地验收完成；验收证据见 [Acceptance](../acceptance/web-dialogue-v1-20261003.md)。技术细化见 [R1 Design](../designs/web-dialogue-v1.md)。

## Problem Statement

现有 ChatBI 已具备账号、查询、多轮追问和受控经营分析，实施前入口是 Streamlit。产品 V1 需要独立网页，便于持续完善聊天、图表、历史与流式体验。R1 先替换现有用户入口，建立登录到查询 / 分析的完整闭环。

用户明确要求只做电脑端，以尽快完成首个可用交付；不加入手机适配和手机验收。

## Solution

- 使用 React + TypeScript + Vite 构建独立电脑端网页，复用 FastAPI 与现有 Application / Domain 链路。
- 一个聊天页面，手动切换“问数 / 经营分析”，默认问数；两种模式的上下文与展示记录分别维护。
- 新网页覆盖登录、首次改密、退出、问数、连续追问、澄清 / 拒绝和经营分析，验收通过后移除 Streamlit。
- R1 只维护当前页面的临时展示；刷新保持登录但进入空白新对话。长期历史由 R3 实现，详细进度与流式由 R4 实现。

## User Stories

1. 作为被管理员创建账号的用户，我可以登录；首次登录须完成改密并重新登录，然后才能使用业务功能。
2. 作为有查询权限的用户，我可以输入完整问题、查看结果表格与经校验执行的 SQL，并在成功结果之后继续追问。
3. 当问题需要澄清、超出能力或执行失败时，我可以看到明确提示，系统不把失败的问题当作成功的查询上下文。
4. 我可以切换经营分析，提交包含目标指标和两个比较时期的自然语言问题，查看报告和查询证据；切回问数后保留原查询上下文。
5. 网络中断后，我能分清明确失败与结果未确认，并按模式选择安全的恢复方式。
6. 我可以退出登录；另一个账号登录后，不会看到上一账号的临时结果，也不会收到上一账号迟到的响应。

## Observable Behavior

### 1. 登录与权限

- 仅管理员创建指定账号，首版无公众自助注册。
- 浏览器使用 HttpOnly Cookie 携带登录凭证，仍由现有数据库 Session 验证账号状态、权限和期限；不在网页可读存储中保存原始 Session Token。
- 刷新后重新核验身份，成功后仍保持登录；没有“记住我”。沿用 30 分钟 Session Idle TTL 与 8 小时 Absolute TTL，不能由前端定时请求无限延长登录。Idle TTL 按后端成功身份校验规则计算。
- `must_change_password` 用户只能进入首次改密流程；改密沿用撤销该账号既有 Session 的规则，完成后重新登录。
- 有 `query.execute` 权限的指定用户可查询同一套销售数据；无权限时禁止业务请求。R1 不增加部门 / 区域行列隔离。
- 长期历史未来按账号隔离，与共享同一套业务数据是两个不同约束。
- 身份过期、账号切换或退出时清理两种模式的临时消息、结果、会话编号、分析任务编号与输入草稿。旧请求的迟到响应不能重新填充这些内容。
- 退出调用后端撤销 Session 并清除 Cookie；网络中断导致无法确认撤销时，清理页面私有内容并明确提示退出未完成、可重试，不宣称服务端会话已撤销，也不自动重新进入业务页面。

### 2. 模式、输入与当前展示

- 默认“问数”；模式切换不自动识别意图，也不自动转换查询条件。
- 每种模式分别保留当前页面内的消息 / 结果与输入草稿；切回问数使用原有效 `conversation_id`。
- “新对话”用于问数，清空当前问数记录、草稿和会话编号；不清空独立的经营分析展示，也不代表取消后端执行。
- 经营分析每个新问题是独立任务，不读取普通问数条件，也不把上一份报告当作跨问题记忆。
- 去除首尾空白后为空的问题不发送；前端只做输入形状检查，不自己裁决业务指标与比较时期。
- 澄清 / 范围拒绝直接显示后端给出的安全说明。用户修改并提交问题后再走现有链路，不新增隐式多轮分析澄清状态。
- R1 页面明确提示：当前阶段刷新会清空对话展示；刷新后即使登录有效，也以空白问数页面开始。不在浏览器持久化聊天结果以替代 R3。

### 3. 普通问数

- 首轮发送完整自然语言问题，不携带 `conversation_id`；成功后保存服务端返回的编号。
- 后续问数携带该编号，保持现有语义修订、认证 / 授权与状态提交规则；客户端不能提交 SQL 或完整语义状态。
- 成功展示原问题、结果表格、返回行数、截断标识和可展开的 SQL。SQL 仅来自成功响应，不显示未经校验的候选 SQL。
- 保留列顺序与值含义，正确区分 `null`、零和空字符串；空结果明确显示“没有符合条件的数据”，仍是成功轮次。
- `truncated=true` 时提示仅显示有界结果，不声称这是完整数据；当前最多返回 100 行。
- 列类型、单位、口径解释、图表推荐与切换属于 R2；R1 不从列名猜测这些业务事实。
- 后端明确失败不改变上一成功状态；`CONVERSATION_UNAVAILABLE` 提示新开对话并提交完整问题，不自动丢弃编号后把片段追问当首轮执行。

### 4. 经营分析

- 继续通过自然语言输入完整问题。页面说明当前支持两个明确时期之间的毛利 / 人民币净销售额变化分析；不新增结构化筛选器或任意分析场景。
- 发送 `mode=analysis`、完整问题与客户端生成的 UUID `analysis_run_id`，不携带普通查询会话编号。
- 新问题生成新 ID；重试本次分析锁定原问题和原 ID，修改问题后属于新任务。
- 成功显示后端报告中存在的标题、摘要、趋势、关键发现、原因说明、建议，以及结构化任务证据。保留后端提供的归因数值与对账结论，不在前端重新计算或补写解释。
- 不把分析相关变化包装成证据不能支持的深层原因；分析失败或证据不足时展示说明，不制造完整报告。
- 相同用户 / 原问题 / 原 ID 的手动重试沿用既有 checkpoint 行为：未完成恢复、完成后读取结果；过期或不匹配时显示后端受控错误，不静默用新 ID 重新执行。

### 5. 请求进行中与恢复

- 页面一次只提交一个业务请求；等待时禁用再次发送、模式切换与“新对话”。仍可编辑下一条草稿、浏览已有结果、退出登录。
- 显示“正在查询”或“正在分析”，不展示虚构阶段或百分比；真正的执行进度、流式和取消在 R4 定义。
- 响应成功 / 明确失败后恢复操作；空结果也结束等待。当前请求与后续草稿分别保存，不能用编辑后的草稿覆盖原请求问题。
- 前端不自动重发业务问题；现有经营分析内部任务的一次基础设施重试不因此移除。
- 网络中断、客户端等待超时、无法识别的响应均不能证明后端没有完成，显示“结果未确认”。停止等待不等于取消服务器任务。
- 普通问数结果未确认时，将该临时会话标为不能继续追问，保留已有展示供查看，提示用户新开对话并补全问题；不基于可能已变化的上下文自动重试。
- 经营分析结果未确认时，允许手动“重试本次分析”，携带原 ID 与问题；不假设原请求已取消，不新增任务状态查询或通用幂等协议。
- 后端明确返回 `QUERY_TIMEOUT` 等受控失败与客户端等待超时分别处理；后者属于结果不确定。
- 登录失效先清理私有页面并要求重新登录；重新登录不能自动重发旧问题。权限拒绝不能以匿名或其他账号回退。

## Implementation Decisions

### 已确认的技术与架构决定

- React + TypeScript + Vite；同一套前端代码用于本地开发和生产打包。
- 本地开发通过 Vite 提供页面和同源 API 代理；上线时页面与 API 使用同一网站地址，生产凭证仅通过 HTTPS 传输。
- 复用 FastAPI，增加浏览器 Cookie 登录支持，保留既有 Bearer 客户端与测试的请求 / 响应兼容。
- 配套 CSRF 防护：覆盖登录、退出、改密及 Cookie 认证的业务 POST；不能只依靠 CORS。Cookie 使用 HttpOnly，生产使用 Secure，并设置适当 SameSite / 作用域。
- Cookie 与 Bearer 同时出现且指向不同身份时拒绝请求，不得静默切换用户；验证失败的显式 Bearer 不能回退到 Cookie。具体接口名称、凭证提取与 CSRF 实现须由设计审查固化，再作为 Ticket 的明确 Contract。
- 前端凭证、输入、模型报告、SQL 和单元格均按不可信内容处理；用安全文本 / 结构化元素展示，不执行服务端返回的 HTML、脚本或 SQL。
- 不引入第二套指标、Prompt、SQL 生成、数据访问或授权逻辑；归因继续由既有确定性后端产生。
- 初始运行目标为单台 Linux / 云服务器并支持本地开发；当前短期会话在进程内，R1 不宣称多 worker / 多副本共享状态。

### 留给设计 / 实施的局部选择

- React 组件拆分、CSS 布局、静态文件挂载方式、开发代理配置和内部状态组织。
- 锁定的兼容依赖版本、包管理命令、测试驱动工具与目录安排；不得以此新增图表、长期存储、SSR、BFF 或业务平台。
- HTTP 等待超时值应与既有同步分析的运行预算核对并在 Design 说明；不能照搬数据库单条 SQL 的 10 秒超时作为完整分析等待期限。
- 验证策略已确定为后端确定性 / 集成检查、真实桌面浏览器验收和真实 AI 闭环；工具名称不改变验收内容。

## Testing Decisions

当前文档不宣称以下验证已运行；实施阶段须提供绑定候选提交的证据。

### 确定性软件验证

- Cookie 与 Bearer 认证、身份一致性、CSRF 拒绝、Cookie 属性及浏览器登录响应 / 日志不暴露原始 Session Token；既有 Bearer 登录响应按兼容 Contract 保留 Token。
- 登录、首次改密、Idle / Absolute 过期、撤销、禁用账号与权限拒绝；无效认证 / CSRF 不进入查询链路。
- 前端模式分离、成功状态提交、澄清 / 失败保持、空结果 / 截断 / 空值显示、重复提交阻止。
- 网络中断与明确失败的区分；普通查询失联后不能继续不确定的追问；分析重试使用原问题 / ID。
- 退出 / 账号切换后清理全部私有状态，旧响应不会写回；退出撤销未确认不能显示为成功。
- 受影响的 API、认证、授权、会话、分析和初始化回归；既有 Bearer / 管理后台仍可使用。

### 桌面浏览器与真实闭环

主要验收环境为桌面 Chrome；以桌面窗口验证可阅读、输入、滚动、展开 SQL 和证据，无手机验收承诺。

| 场景 | 验收结果 |
| --- | --- |
| 首次账号 | 登录 → 强制改密 → 重新登录 → 进入问数；改密前不能查业务数据 |
| 查询与追问 | 完整问题成功、表格 / SQL 正确展示；追问使用当前成功上下文 |
| 模式切换 | query → analysis → query，展示和上下文不串用 |
| 分析 | 明确两期指标的报告与后端证据一致，重试不生成第二个任务 ID |
| 空 / 拒绝 / 失败 | 不伪造结果，不污染上一成功状态，提示与后端错误一致 |
| 刷新 | 登录有效时仍登录，但回到空白问数；不恢复临时消息 |
| 等待与失联 | 操作限制生效；明确失败和结果未确认分别恢复；普通问数提示新对话 |
| 身份变更 | 退出 / 过期 / 换号后私有展示清空，迟到响应不能出现 |
| 打包入口 | Vite 开发入口和打包后的网页均能通过同源 HTTP 调用后端，不依赖 Streamlit |

- 真实浏览器通过真实登录 / HTTP 完成普通问数、连续追问与经营分析到模型、SQL Guard、PostgreSQL 的闭环；仅 TestClient 或假的查询结果不能代替这些证据。
- 软件异常场景可使用确定性服务替身验证，需与真实 AI 证据区分。
- 根据最终 Diff 判定适用 AI Evaluation；语义、Prompt、模型配置和核心链路未变时说明既有基线适用范围，不把 `6a5e6cc` 报告改称新候选报告。
