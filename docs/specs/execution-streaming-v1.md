## Problem Statement

R1–R3 已提供电脑端问数、独立经营分析、结果展示及私人历史 / 成果。网页当前等待完整 JSON，仅能显示正在查询或分析；不能实时查看阶段或报告生成，也没有服务端取消接口。断连后后台可能仍执行，页面不能及时获取原执行的进度。

R4 在同一业务链路增加真实执行状态、SSE 反馈、取消与重连，先实现并验收执行状态与最终结果，再实现并验收分析文字真实增量展示。

事实源：[Roadmap](../roadmap.md)、[产品范围](../product-scope.md)、[Architecture](../architecture.md)、[Domain](../../CONTEXT.md)、[R3 Spec](history-results-v1.md)、[R3 Design](../designs/history-results-v1.md)、[Query API](query-api.md)、[Web Spec](web-dialogue-v1.md)、[R2 Spec](result-visualization-v1.md)、[Evaluation](evaluation.md)、[Runbook](../runbook.md)。R4 确认后扩展网页执行 Contract；旧同步 API 的适用边界保持。

## Solution / Scope

- 网页历史问数、追问、显式重查及独立经营分析的执行统一具有可查询身份与状态；分析恢复也受相同执行管理约束。
- POST 提交 / 取消，GET 查询状态 / SSE 订阅已有执行。受理成功后返回执行编号；订阅不承担业务执行。
- 浏览器断连、刷新、关闭后后端继续执行；重开历史获取原执行状态与结果，仍执行则重连。
- 问数与分析均支持主动取消；区分停止请求已接受和执行真正结束。
- 分析报告文字随真实模型输出逐步展示，最终结构、引用与业务校验以及持久化成功仍是正式报告的门槛。
- 复用现有 FastAPI、账号 / Session / 权限、Control DB、R3 历史和查询 / 分析链路，单 API 进程运行。

Change Profile: 持续维护、跨模块且高风险；涉及公共 API、后台执行生命周期、持久化提交、取消竞态、权限与模型流式 Adapter。完整 Spec 确认后设计审查，通过后形成 Ticket 草案与 Readiness，拆分及实施授权确认后编码。

## User Stories

1. 提问或追问时看到真实执行阶段，成功后查看已保存的表格 / 图表。
2. 分析时看到实际任务计数与生成中的报告文字，完成后获取正式报告并可保存成果。
3. 刷新、关闭或网络断连后重开历史，连接原执行，不重复调用模型或查询。
4. 主动取消并知道是否真正停止；停止前不误以为可以再次提交。
5. 受理响应丢失时找回原执行；重复操作不创建第二次执行。
6. 权限失效、超时、保存失败与服务重启时获得明确状态，既有成功结果和续聊上下文不被失败污染。

## Observable Behavior

### 1. 身份、受理与幂等

历史归属、历史轮次、分析 run、一次执行、一次提交操作分别表达不同身份。分析恢复可沿用原 run，但新增执行尝试；模型内部重试仍属于同一执行，不生成新历史。

- 明确提交前生成稳定操作编号。受理检查当前身份、归属、权限、CSRF、适用 revision、执行占用与额度；受理持久化成功后才允许进入业务执行。
- 同编号、同请求只对应一次执行；重复提交返回原执行状态 / 身份，不重执行。编号与请求内容不匹配则受控拒绝。
- 受理响应丢失时按操作编号查回原执行；查到则获取状态 / 订阅。暂时查不到显示受理结果未确认，不自动换编号重发；用户明确再次提交复用原编号。
- 查回与重复受理仍检查当前归属 / 权限，不因持有编号放行；revision 校验和去重的顺序须保证原请求不会因已完成而错误变成新执行。
- 受理前持久化失败拒绝请求、不执行；受理 / 提交结果不确定时不自动重放。

### 2. 状态与真实进度

| 可观察状态 | 含义 |
| --- | --- |
| 已受理 / 执行中 | 已对应唯一执行；只呈现已经发生的阶段 |
| 正在取消 | 已接受主动取消，执行尚未确认结束 |
| 超时，正在停止 | 总时限已到，执行尚未确认结束 |
| 成功完成 | 适用校验与结果 / 成功上下文持久化均成功 |
| 明确失败 / 澄清 / 拒绝 | 受控非成功终态，上一成功上下文不变 |
| 已取消 | 已确认执行结束且取消裁决生效 |
| 执行超时 | 已确认超时停止；非成功终态 |
| 结果未确认 | 无法证明成功提交或完成，不等同于已取消 / 失败 |

连接中断是订阅状态，不是执行终态。授权失败保留受控原因；失败状态落库也失败时，不宣称已保存失败。

| 模式 | 阶段 |
| --- | --- |
| 问数 | 理解问题 → 检索业务信息 → 生成查询 → 安全校验 → 查询数据 → 保存结果 |
| 分析 | 理解分析目标 → 校验分析计划 → 执行查询任务 → 计算归因 → 生成报告 → 校验并保存 |

只发送实际进入的阶段；已有认证语义可跳过不发生的步骤，恢复可从实际执行位置开始，不伪造完整阶段遍历。分析计划确定后展示实际任务完成计数，例如 2/4；内部重试不重复计数。终态不可被迟到阶段覆盖。

不显示估算百分比、内部 Prompt、模型推理。问数 SQL 继续遵守校验完成后查看的原边界，分析不新增 SQL 公开能力。表格 / 图表在成功且结果有效后展示。

### 3. SSE 与重连

- POST 受理与取消，GET 状态查询与 SSE 只观察已有执行；路由和 DTO 在 Design 中明确，不能借协议连接触发执行。
- 每次连接先同步当前执行状态、已有草稿及其版本，再接收增量；重开历史据当前执行订阅，不重新提交原问题。
- 事件 Contract 必须区分状态快照、阶段 / 任务计数、文字增量、草稿重置、终态及连接控制。业务数据携带执行身份与可排序序号；模型生成尝试变化必须可识别，以隔离旧草稿。
- 快照与增量衔接必须没有丢失窗口；重复、乱序、旧执行 / 旧生成尝试事件不得造成重复文字、状态回退或跨任务更新。序号仅保证当前执行的一致观察，不承诺持久化完整事件日志。
- 完成后读取已保存的正式结果并关闭连接；终态期间仍可查询状态，不依赖终态事件恰好送达。
- 首版不持久化完整事件流水；重连通过当前快照恢复观察，服务重启按第 6 节处理。事件缓存与慢订阅者缓冲必须有界，不能阻塞业务执行；失去增量连续性时重新同步快照，不静默拼接缺失文字。
- GET / 重连不延长登录期限，不写入新的业务轮次。网络断连仅触发状态查询与重连，不据此取消或重试执行。

### 4. 取消、超时与完成竞态

- 问数和分析均提供取消执行。点击后显示正在取消，后端停止后续步骤并尽力中断当前调用；不承诺模型 / DB 立即中断。
- 确认执行真正结束后才显示已取消并解除占用，此前禁止同账号再次提交。已取消轮次不提交成功结果、不推进上下文，保留上一成功结果。
- 已提交的成功结果优先作为已完成显示，取消不撤销成功。取消生效与成功提交必须由服务端串行裁决，不允许已取消之后成功回写或两种相互矛盾终态。
- 同一执行重复取消不得创建新操作副作用；连接失联不表示取消请求已生效，应查询原状态。
- 服务端总时限：问数 180 秒、分析 1200 秒，涵盖该次执行的全部步骤与内部重试，重试不重置时限；分析手动恢复属于新执行尝试，原 checkpoint 24 小时期限不延长。
- 达到总时限显示超时正在停止；停止后续步骤并尽力中断调用，真正结束才释放额度，不提交成功或推进上下文。保留当前单模型调用与 SQL 查询的超时限制。
- 总时限是资源边界，不是性能指标。订阅断连或暂时无文字不裁决超时；服务重启不靠时限假设旧执行停止。

### 5. 草稿与内部重试

- 标题、摘要、关键发现、趋势判断、原因分析、行动建议逐步展示真实模型文字增量，标明生成中 / 尚未校验，不能另存成果。
- 不拆字播放已完成报告，不公开原始 JSON；最终报告结构及业务范围沿用既有 Contract。归因数值、图表与任务证据在最终校验且保存成功后展示。
- 正式报告校验 / 保存成功后替换草稿，才允许另存成果。执行失败、校验失败、确认取消后清除本次草稿并显示原因，保留此前成功结果；超时停止完成按非成功结果处理。
- 仅网络断连保留当前页面已有草稿并标记连接中断，重连以当前服务端草稿 / 状态 / 最终结果为准。刷新可从当前执行快照恢复，不承诺重启后恢复临时草稿。
- 保留报告生成模型调用异常时最多一次内部重试：同执行显示报告生成重试中，显式清除上一尝试草稿，从新尝试重新展示；重连只得到当前尝试草稿。校验失败不自动重试。
- 取消、超时、授权失效后不发起内部重试；两次尝试共用总时限。既有分析查询任务内受控重试次数不扩大，受相同停止 / 授权 / 总时限约束。
- 生成文字与公开错误按不可信纯文本展示。精度、快照 5 MiB 上限与超限 / 保存失败边界沿用 R3，不截断报告或证据来换取成功。

### 6. 失败、恢复与服务重启

| 情况 | 行为 |
| --- | --- |
| 断连 / 刷新 / 关闭 | 后端继续，重开连接原状态，不重发业务请求 |
| 原执行仍在进行 / 正在停止 | 查询 / 观察原执行，禁止再执行，不自动重试 |
| 问数明确失败 / 已取消 | 手动重新发送新增轮次，沿用上一成功上下文，保留原轮次状态 |
| 分析明确失败 | checkpoint 有效期内手动恢复原问题 / 原 run |
| 分析已取消 | 原问题新建分析任务，不恢复已取消任务 |
| 澄清 / 权限拒绝 / 条件不支持 | 提示补全或处理权限，不提供盲目重试 |
| 保存失败 / 快照超限 | 结果未确认、不提交成功或推进上下文，不自动重试；显式恢复仍受原归属 / 期限规则约束 |
| 服务重启，结果已保存 | 展示正式快照，不执行 |
| 服务重启，无法确认完成 | 标记结果未确认、不自动续跑；问数从上一成功轮次继续，分析 24 小时内手动恢复，过期显式新建 |

不增加重启自动续跑。旧执行迟到结果不能覆盖新状态、已删除历史或别的账号。旧分析 checkpoint 已完成但网页未确认保存的情形按 R3 协调规则处理，不把模型 / checkpoint 完成等同于网页成功。

### 7. 身份与权限失效

- 新接口检查当前身份、历史 / 执行归属及当前权限；Cookie 写操作保留 CSRF。执行编号、操作编号不是授权凭证。
- SSE 推送前重新检查身份 / 权限；失效停止推送、关闭连接，页面清除私有内容，提示重新登录或无权限。
- 后端发现原登录失效、账号禁用或查询权限撤销后停止后续步骤并进入停止流程，执行真正结束才解除占用。网络断连本身不代表授权失效。
- 最终成功提交前重新鉴权，未通过不提交成功 / 不推进上下文。权限恢复不自动续跑，依已确认规则显式操作。
- 推送 / 重连鉴权与后端执行鉴权不能依赖浏览器持续在线；不靠心跳续期 Session。既有登录期限保持。
- 日志与事件不得暴露凭证、完整 Prompt、checkpoint 私有对象或内部异常。HTTP / SSE 不拥有业务口径；LLM 候选仍经确定性校验与 SQL Guard。

### 8. 并发与资源

- 默认每账号 1 个后台执行、单 API 进程 4 个执行，问数 / 分析共用额度，可配置。包括 R4 新提交、恢复和重查；旧同步 API 响应 Contract 不迁移。
- 超限立即提示已有执行或服务繁忙，不排队 / 自动重试。受理去重不能重复占额度。
- 同一对话仍只有一个执行，revision 落后仍要求刷新；执行期间禁止删除，既有结果可查看 / 另存。取消 / 超时停止中继续占额度，确认结束才释放。
- 同一任务可在多个页面观察，不重复占执行额度。订阅资源与执行资源分开管理，慢连接 / 重连 / 页面关闭不得泄漏资源；具体缓冲和连接管理在设计中给出有界方案。
- 默认值是资源保护配置，不代表容量验收完成，不引入排队系统或多副本协调。

## Implementation Decisions / Design Constraints

| 决定 | 依据与约束 |
| --- | --- |
| HTTP POST + GET SSE | 用户已确认；提交与观察解耦，连接不能触发查询 |
| 同一执行链 | 复用 Online Query / Business Analysis，不建立第二套业务 / SQL 生成 |
| 当前状态快照 + 增量 | 支持重连 / 多页面，不建设完整持久事件流水 |
| 成功必须校验并持久化 | 延续 R2 / R3，草稿和 checkpoint 不是正式成功 |
| 单 API 进程 | 延续已确认运行边界，多 worker / 多副本不在本次承诺 |
| 先状态与最终结果、再文字流式 | 用户确认的实施与验收顺序，全部纳入 R4 |

Interface 处理身份与协议；Application 裁决受理、执行、取消、占用、提交与恢复，通过 Port 使用 Adapter；Domain 和认证语义仍拥有业务真相。事件从实际业务步骤产生，不把 Trace Exporter 当执行状态事实源。

留给设计的局部决定：路由 / DTO 精确字段、事件版本与命名、执行尝试和原分析 run 的映射、后台调度 / 生命周期组织、停止检查点与 Provider 中断能力、事务 / fencing、流式结构解码、快照与增量的原子衔接、有界缓存 / 连接管理、配置名称与 migration。必须证明已确认行为；需改稳定边界则返回用户确认，不在实现中猜测。

沿用 Runbook 的 Python 全量、隔离数据库、前端类型 / 构建 / Playwright、静态 / 模块边界 / 锁文件 / 文档 / 安全检查入口；受影响链路新增 Regression。报告身份遵守 Evaluation Contract，历史报告不重标为新 HEAD。

## Compatibility / Migration / Documentation

- `/api/v1/query` 仍为同步 JSON，旧 Bearer 客户端无需迁移；新能力不得意外改变默认查询 / 分析业务行为。
- 既有历史 / 成果、成功上下文、精度、TTL、owner 隔离与 5 MiB 快照限制保持。执行新增状态与存储如需迁移，在 Design 明确幂等升级、旧数据兼容与保留数据回滚。
- 不得通过旧入口或 checkpoint 直接恢复已取消分析，设计需证明共享执行语义的协调；原 API 的正常请求 / 响应兼容不免除防止同 run 冲突。
- 实施 Done When 包含正式 R4 Spec / Design / Acceptance、Query API / Web / R3 受影响 Contract、Architecture / Product Scope、README / Runbook / Roadmap 的维护或不适用理由。
- 本 Spec 是规划期间 R4 行为来源，确认后设计 / Tickets 引用它；正式 `docs/specs/` 在实施交付时承接 Contract，不留互相冲突副本。
