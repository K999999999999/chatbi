# R3 历史与成果管理

状态：已确认行为 Contract；当前本地候选及验收状态见 Git 公共目录的本机实时工作状态，尚未发布。来源为用户确认的六项整体目标；过程记录保留于 `.scratch/history-results-v1/`。

## Problem Statement

R1 / R2 已交付电脑端问数、独立经营分析、可信结果说明和图表，但网页刷新仍清空临时记录。普通问数仅有进程内短期会话，分析 checkpoint 仅支持限时恢复。用户不能在重新登录或服务重启后重开长期历史、继续问数，或保存独立成果。

本目标为产品 V1 已确认路线中的 R3，后续 R4 流式 / 详细执行状态、R5 导出、R6 / R7 生产运行验收仍独立推进。

事实源：[路线图](../roadmap.md)、[产品范围](../product-scope.md)、[架构](../architecture.md)、[领域上下文](../../CONTEXT.md)、[Web Spec](web-dialogue-v1.md)、[Query API](query-api.md)、[R2 Spec](result-visualization-v1.md)、[多轮原 Contract](../../.scratch/multi-turn-conversation-v1/spec.md)、[分析原 Contract](../../.scratch/business-analysis-root-cause-v1/spec.md)、[Evaluation Contract](evaluation.md)。历史阶段约束不反向否定本轮确认的网页历史恢复行为；本 Spec 整体确认后明确其与旧短期接口的适用边界。

## Solution / Scope

- 网页问数对话、独立分析任务自动保存长期历史，按账号隔离；可列表查看、搜索、重开、重命名和删除。
- 重开读取当时结果快照，不自动查询；普通问数可恢复最后一次成功的结构化条件继续追问。
- 用户可将一次成功查询或完成分析报告另存为具名成果，结果快照固定，生命周期与原历史独立。
- 现有 PostgreSQL `chatbi_control` 新增专用历史 / 成果表，前端通过现有 FastAPI 读写，复用既有查询 / 分析执行链路。
- 历史持久化属于网页成功条件；结果快照与续聊状态一致提交，多页面并发、断连、重启与迟到提交有确定性保护。
- 现有 Bearer Query API 默认维持原短期会话 Contract，不强制保存长期历史。

## User Stories

1. 问数并追问，刷新后仍能看到该对话的原问题、结果、图表及失败轮次；重新登录可从历史列表打开。
2. 过期或服务重启后重开自己的问数历史，继续“改成毛利”等追问，程序沿用最后成功轮次的完整业务条件并查询当前数据。
3. 查看历史的当时结果，需要最新数据时显式重新查询；新结果形成独立记录，原历史和成果不被覆盖。
4. 保存成功查询或完成报告为具名成果，删除原历史后仍能查看成果；删除成果不影响历史。
5. 重开未完成分析，在有效 checkpoint 期限内手动恢复；过期后查看历史并显式新建任务。
6. 多页面、网络断连、保存失败或权限变化时，获得明确状态，不发生重复自动执行、上下文错位或跨账号泄露。

## Observable Behavior

### 1. 历史、轮次与成果

| 对象 | 内容与生命周期 |
| --- | --- |
| 问数历史 | 对话归属、标题、问题与轮次状态、成功结果快照及最后成功结构化条件；可跨刷新 / 登录 / 服务重启重开 |
| 分析历史 | 一次独立分析的问题、任务身份、状态与完成报告快照；不继承问数条件 |
| 成果 | 用户命名、所选成功轮次或完成报告的独立快照及必要来源说明；原历史更新 / 删除不改变其内容 |
| 短期问数会话 | 旧 API 的进程内 30 分钟无成功更新 TTL 保持；网页历史续聊通过自己的持久上下文恢复，不简单延长旧 TTL |
| 分析 checkpoint | 原 24 小时恢复期限保持；历史 / 成果与其独立，不靠延长 checkpoint 保存报告 |

历史及成果均保留至用户主动删除，不按天数自动清理。成功快照保存当前接口已经返回的完整公开结果、原始值、结果说明、截断标记及适用报告 / 证据；使用 R2 展示规则重建表格和图表，保留当时口径，不重新计算指标或归因。保存成果应保留重查所需的完整业务条件或原分析问题，不能只依赖可能被删除的历史引用。

图表展示复用当前 R2 组件与安全降级；本目标不承诺保存图表切换、折叠、草稿等临时偏好。查询成功但空结果仍属于成功轮次，可作为续聊基础或另存成果。

### 2. 自动记录与失败轮次

对已认证、已按权限受理的网页业务请求自动记录问题。成功、业务澄清、范围拒绝、执行失败分别保留其可公开状态及受控错误；无有效身份或无访问权限不得创建属于其他账号的历史，也不得进入业务链路。

- 只有成功轮次才能替换最后成功的结构化上下文；失败 / 澄清 / 拒绝保留上一成功状态。
- 非成功轮次不能另存为成果；分析报告只有完成并通过现有适用校验后才可另存。
- 未确认完成显示“结果未确认”，不假称成功或已取消；重开不自动重试。
- 无成功轮次的问数历史没有可继承上下文；下一次问题按完整首轮问题处理。
- 历史 API 不暴露内部异常、连接配置、凭证或不可公开的模型 / checkpoint 对象。账号与权限拒绝继续遵守当前安全边界。

### 3. 重开、刷新与重新登录

- 重开历史或成果默认读取当时快照；不调用 LLM 或业务查询数据库来更新结果。
- 刷新重新核验身份，从后端恢复当前打开的问数对话或分析任务；不得自动重发原请求。
- 重新登录默认新问数对话，用户从历史列表选择旧记录；不自动恢复其他账号的页面内容。
- 记录不存在、已删除或当前身份无权访问时提示不可用，回到新对话，不泄露其他账号记录存在性。
- 退出、身份过期和账号切换清除私有页面状态；迟到响应不得重新填充。沿用 Cookie、CSRF、Session 期限及指定账号规则，不周期保活登录。

### 4. 历史续聊与业务定义变化

普通问数历史恢复以服务端最后一次成功查询的结构化条件为依据，包括原指标、时间、维度、筛选等，不以聊天全文、旧 SQL 或图表数值作为业务真相。短期会话过期或服务重启后仍可续聊；新追问重新鉴权、校验当前业务定义，查询当前数据，并新增轮次及快照。

用户本轮确认补齐服务端结构化条件与确定性校验：完整恢复包括既有已支持的排序、Top-N业务数量、实体选择 /去重及聚合筛选等实际业务条件。模型提出候选，程序按权威语义和当前发布资产认证；SQL Guard检查执行与完整条件一致，不能从旧SQL推断遗失含义或保存成功后拒绝正常恢复。旧API默认行为保持；具体字段与合并规则见[结构化恢复Contract /设计](../../.scratch/history-results-v1/restoration-semantics.md)。

既有同槽位替换、不同槽位叠加、明确维度替换及歧义澄清规则继续适用。不新增跨查询比较、自动路由到经营分析或模型自由恢复上下文。

旧结果按当时口径展示；续聊和重查须校验当前指标定义及认证物理映射。旧条件不兼容时提示新开对话、补全问题，不自动换指标、改口径或执行旧 SQL。历史状态是待验证数据，不是授权凭证或永久有效的语义认证；自然语言 → 业务语义 → SemanticQuery → 认证物理映射 → SQL 的链路及确定性 Guard 保持。

### 5. 显式重新查询

- 问数从所选成功轮次 / 查询成果的完整业务条件新开对话，重新鉴权并走当前查询及 SQL Guard 链路。
- 分析从原问题 / 报告成果以新任务编号执行，仍为独立任务。
- 原历史 / 成果快照不覆盖，新结果可再另存为新成果。
- 失败、拒绝或条件不兼容时返回受控状态，不把新任务失败写成原成果发生变化。

### 6. 分析恢复

重开只读取已保存状态，不自动执行。原 checkpoint 仍有效时，当前合法用户可用原问题 / 原任务编号手动恢复；不同用户或不同问题不得复用该编号。超过原 24 小时期限后历史仍能查看，但只能显式新建任务重新分析，不静默复用过期 ID。

完成报告快照长期保留，读历史不依赖 checkpoint 仍存在。未完成报告不能另存成果。原分析任务内的受控重试规则保持；本 Spec 禁止的是页面重开 / 断连后的自动重发，不删除既有业务执行中的受控重试。

### 7. 成功提交与持久化失败

| 情况 | 可观察结果与状态 |
| --- | --- |
| 执行前无法写入历史 | 拒绝本次业务请求，不进入查询 / 分析执行，不宣称已受理 |
| 查询 / 分析完成且持久化成功 | 成功结果快照与适用续聊状态保存后才能返回成功 |
| 执行后无法保存或快照超限 | 明确提示保存失败 / 结果未确认；不推进最后成功上下文、不返回成功、不自动重试 |
| 业务失败且历史可写 | 保存受控失败状态，保留上一成功上下文 |
| 失败状态本身也无法落库 | 不宣称已保存该失败；保留既有已提交状态，待恢复后按未确认轮次规则处理 |

程序须保证快照与网页续聊提交一致；不能页面显示成功、刷新后缺失结果，或保存失败后下一轮仍继承未提交上下文。销售业务查询仍只读；不会为恢复历史重放已执行请求。独立分析 checkpoint 可能已推进，不因此把网页历史保存失败认作成功；再次恢复必须由用户显式触发并遵守既有归属 / 期限规则。

### 8. 并发、断连、重启与迟到结果

- 同一问数对话 / 同一独立分析任务同时只受理一个执行请求；其他页面提示正在执行，不排队、不自动重试，不进入下游执行。
- 问数提交所依据的上下文落后于最新成功轮次时，要求刷新历史后再追问，不在用户不知情时切换上下文。
- 执行期间禁止删除该对话 / 分析历史；仍可查看或另存既有已完成结果。保存成果不改变执行占用或续聊状态。
- 浏览器断连不代表后端已结束；后端仍执行时保持占用，重开只读当前已保存状态。
- 服务重启后，无法确认完成的轮次标为“结果未确认”；问数从上一已提交成功轮次继续，分析按原 checkpoint 规则手动恢复。
- 占用回收与新请求受理须由服务端裁决；旧执行迟到结果不能覆盖恢复后新状态、已删除历史或其他账号页面。
- 具体事务、版本校验、占用和回收机制在 Design 中证明上述不变量。当前首版仍按既有单 API 进程运行边界验收，不新增多 worker / 多副本可用性承诺。

### 9. 列表与删除

历史按问数 / 经营分析区分，按最近更新时间排序，支持分页、标题搜索、重命名、删除；默认标题为首个问题的简短文本，不额外调用模型。成果列表支持打开、标题搜索、重命名、删除；保存时用户填写名称，允许同名。

删除问数对话删除其历史轮次；删除分析任务删除该任务的历史。已另存成果保留；删除成果不影响原历史。已删除历史不得通过原历史编号重开、续聊或在历史恢复入口重新执行。原问题以新任务明确重新查询不等同于恢复被删除记录。

删除与执行受理必须互斥判定；不能在用户删除后由迟到提交复活历史。具体删除存储形式由设计明确，必须满足不可读 / 不可续聊与独立成果保留；不能只在列表隐藏而允许详情访问。

### 10. 资源、精度与安全

- 快照完整保存当前接口公开返回结果，问数仍最多 100 行；截断提示及结果说明同时保存，不获取全量数据。
- 单个结果快照上限 5 MiB（5 × 1024 × 1024 字节）；以持久化快照的 UTF-8 JSON 编码大小检查。查询快照包含数据及说明；分析快照包含报告及公开任务证据。超限明确报错并按保存失败规则处理，不静默丢行 / 丢证据。
- 历史与成果列表默认每页 20 条、最多 100 条，详情按需加载；不在列表响应中附带全部结果快照，也不一次下载全部历史。
- 保存原始返回值和类型，不将高精度十进制字符串转换为浮点后持久化；沿用 R2 可信说明、NULL / 零 / 空字符串、截断及未知版本降级。
- 所有读取 / 修改 / 删除 / 续聊 / 重查 / 恢复操作核验当前账号、归属及当前权限，用户历史私有；首版仍共享同一套业务数据，不新增行列级隔离。
- Cookie 写操作保留 CSRF，客户端提供的用户编号不决定归属；返回标题、问题、SQL、报告均作不可信文本显示，不执行 HTML / 脚本。
- 不持久化登录凭证或 AuthContext，不把内部路径、Secret、完整模型 Prompt 或 checkpoint 私有对象复制到公开快照。查询 SQL 的查看入口及分析不公开 SQL 的现有边界保持。

## Implementation Decisions / Decision Record

| 决定 | 依据与取舍 | Revisit Trigger |
| --- | --- | --- |
| 快照重开、显式重查生成新记录 | 用户逐项确认；可核对原结果且避免打开历史隐式产生执行成本 | 明确的新版本对比需求 |
| 持久结构化状态恢复问数 | 用户确认过期 / 重启后续聊；旧快照不成为当前业务真相 | 当前语义或映射不兼容 |
| 自动历史与手动独立成果 | 用户确认；原历史删除不损坏已保存成果 | 明确共享 / 导出需求 |
| PostgreSQL Control DB 专用表 | 复用已核实的账号 / checkpoint基础设施与迁移入口；不将状态写入销售只读库 | 经确认的规模或部署变化 |
| 网页持久化成功门槛 | 用户确认；快照及续聊上下文一致，失败不暗中推进 | 已确认的新可用性取舍 |
| 旧 Bearer 接口维持短期行为 | 用户确认；兼容现有客户端、测试与评测入口 | 显式向外部调用方提供长期历史 |
| 单进程运行边界内验证 | 延续已确认初始运行边界；持久历史不等同于多副本能力 | R6 / R7 新运行 Contract |

职责边界：Interface 处理 HTTP / Cookie / 输入输出，Application 裁决历史归属、轮次受理、成功提交和恢复；通过 Port 使用 Control DB Adapter，Domain 与业务语义仍拥有业务真相。Online Query 不承担历史、账号或成果管理；Infrastructure 不定义指标和权限。具体模块组织由设计审查明确，不能新增第二条生成 / 执行链路。

## Testing Decisions / Acceptance

以下是已确认的验收门槛。运行结果与候选身份以 [Acceptance](../acceptance/history-results-v1.md) 的入口及本机报告为准，不能从行为 Contract 推断已通过。

| 场景 | 可观察验收与证据 |
| --- | --- |
| 登录 → 查询 → 追问 → 刷新 → 重登录 | 原问题与每轮状态、结果说明 / 表格 / 图表恢复正确；重登录默认新对话，重开无模型 / 查询调用 |
| 短期过期 / 重启后续聊 | 从最后成功业务条件继续，真实新结果与独立 SQL 参考一致；失败轮次不改变基础 |
| 显式重查 | 新对话 / 新分析任务，新数据与当前口径正确，原历史 / 成果不变 |
| 保存与独立删除 | 成果内容固定；删原历史成果仍读，删成果历史仍读；旧历史ID不可读 / 续聊 |
| 失败与超限 | 受理前写失败不调用下游；执行后写失败不推进状态；5MiB边界精确，超限不静默截断 |
| 多页面 / 执行中删除 | 仅一个执行，过期版本拒绝，执行中删除拒绝；无并发失序或复活 |
| 断连 / 重启 / 迟到 | 重开不重发，正在执行保持占用；重启未确认状态可处理，旧结果不能覆盖新状态 |
| 分析checkpoint期限 | 有效期限内原任务手动恢复，过期只能新任务；完成快照独立于checkpoint清理，失败报告不可保存 |
| 安全与当前权限 | 跨账号、权限撤销、禁用、CSRF、恶意标题 / 文本无越权与注入；拒绝路径无下游执行 |
| 定义变化 | 旧快照保留原口径；不兼容续聊 / 重查拒绝，无自动指标 / 口径替换 |
| 持久化与运行 | 新环境初始化、旧库升级、可重复migration / 权限 / 启动检查、重启与持久数据一致 |
| 兼容与回归 | 旧Query API默认无长期历史，原短期错误 / TTL不变；R1 / R2展示与两模式隔离不回归 |

### 验证层次与报告身份

- Software Test：Application / API公开状态边界的确定性测试，注入明确的持久化 / 时间 / 下游失败；覆盖提交、归属、版本 / 并发、删除、重启、超限和兼容，不以仅检查私有实现调用顺序代替行为证据。
- PostgreSQL Integration：真实Control DB事务、migration、权限、持久化版本和独立成果；无真实业务数据写入。
- 浏览器：电脑端Chrome真实页面操作及故障注入，包含身份换号 / 权限变化 / 刷新 / 断连；沿用打包同源与Vite开发入口适用检查。
