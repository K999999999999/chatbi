# 基础 Multi-Metric Retrieval（多指标在线检索）规格

状态：已确认设计方向，规格同步完成，待实现设计

日期：2026-09-08

范围：现有 Online Retrieval（在线检索）与 Online Query（在线查询）的增量行为契约。

本文完成规格设计，不表示实现完成或业务验收通过。第 12 节的业务决策已按本次讨论确认；基线事实源已完成同步，下一步进入实现设计。

## 1. 目标与最小范围

支持用户在一个问题里明确请求多个已登记指标，按同一组维度、相同日期和固定过滤口径，生成并执行一条只读 SQL，完整返回全部请求指标。

主验收问题：按客户类型统计已完成订单数、人民币销售额和毛利率。

预期结果每行包含客户类型、已完成订单数、人民币净销售额、毛利率。三个指标都必须有权威定义、被有效召回并通过兼容检查；任何一个未确定，都不能只回答剩下几个。

当前五个指标足够，本阶段不新增业务指标。基础范围限定为：

- 同一业务主题、同一个事实表 data_source。
- 相同 time_field、相同指标固定 filters。
- 所有指标共享用户提供的日期范围、分组维度及查询级过滤条件。
- 原子指标和派生指标均可；每个指标已经具有直接引用物理字段的完整公式。
- 一次同步请求、一次 SQL 生成调用、一条 SQL、一个结果集。
- 请求多个指标只是并列输出，不包含用户临时定义的新公式或多步骤分析。

后续范围：跨事实表汇总、不同指标分别指定日期或过滤条件、同比环比编排、跨粒度计算、递归指标编译、多轮对话、经营分析、权限及生产化治理。

## 3. 业务对象

| 对象 | 含义 | C05 示例 |
|---|---|---|
| 请求指标 | 用户明确要求输出的指标 | 已完成订单数、人民币净销售额、毛利率 |
| 指标别名 | 同一个指标的另一种叫法 | 人民币销售额 → 人民币净销售额 |
| 分组维度 | 将各指标按相同分类汇总 | 客户类型 |
| 指标固定条件 | 权威口径的一部分 | order_status = 'completed' |
| 用户查询条件 | 本次查询的共同范围 | 2025 年第一季度、客户类型为经销商 |
| 公式必需列 | 计算已选指标所需的字段 | order_id、net_sales_amount_cny、sales_cost_amount_cny |
| 依赖指标 | depends_on 表达的血缘 | 毛利率依赖人民币毛利、人民币净销售额 |

只把用户明确请求的指标放入最终输出清单。查询毛利率时，不因为 depends_on 自动要求输出毛利、销售额或成本。

当前每个派生指标已含完整物理公式，直接使用它并合并字段引用即可。在线无需递归检索依赖指标；原子指标登记与在线递归展开是两件不同的事。

## 4. 请求识别与逐指标召回

### 4.1 基础表达范围

首版支持明确的正向列举，例如：

- 按客户类型统计已完成订单数、人民币销售额和毛利率。
- 查询销售额与销售成本。
- 按产品线统计销售额、销售成本、毛利和毛利率。
- 2025 年第一季度按销售区域统计毛利和毛利率。

维度、日期、查询条件与指标列举片段需区分。不能把“按客户类型和销售区域”误认为两个指标，也不能从“客户名称中包含毛利率”推断用户请求毛利率指标。

识别不确定、否定表达、分别指定口径、未登记计算或无法解释的列举项，受控停止。首版不承诺理解任意自然语言句式；实现设计必须给出支持的片段边界与正反例，不能仅靠删除全部标点后的全文子串匹配。

### 4.2 指标身份确认

使用同一发布版本的全部指标名称、别名和 document_id 形成轻量名称映射，识别用户明确列出的请求项。该映射是已有 METRIC 元数据的派生查找表，不是新业务事实源。

当前 AssetSnapshot 没有完整名称映射，后续实现需补齐其加载能力。从已发布 METRIC 集合读取名称元数据并按 build_id 缓存；不读取未发布的 metrics.json 充当当前在线资产，也不把全部公式注入 Prompt（提示词）。具体读取方式及完整性检查在实现设计中验证。

匹配规则：

1. 保留提及位置和片段边界，同一位置重叠名称采用最长有效匹配：“毛利率”不额外命中“毛利”。
2. 不同位置独立保留：“毛利和毛利率”必须识别成两个指标，不能用全句最长名称覆盖其他指标。
3. 名称和别名映射到规范指标身份；按身份去重，保留用户第一次提及顺序。
4. “销售额、人民币销售额”输出同一个规范指标，不重复计算两列。
5. 同一有效名称对应多个指标时返回歧义，不按向量分数替用户决定口径。
6. 列举片段中存在无法映射的项时整次拒答。例如“销售额和未登记的退货率”不能退化成只查销售额。
7. 当前首版多指标只接受能够映射到已登记名称或别名的明确请求；宽泛描述的单指标请求保留基线语义召回行为，不把不完整多指标误归入该分支。

### 4.3 METRIC Dense Retrieval（指标稠密检索）

每个去重后的请求指标分别进行 METRIC 检索，使用该指标请求片段及已确认规范名称构成查询。两条并列指标有两份检索证据；不以整句一个 Top-K 代替完整指标集合。

- METRIC 不受 TABLE 候选表过滤。
- 每个请求项必须在其检索结果中有效命中相同 document_id，且满足指标阈值。
- 名称匹配证明用户想查谁，向量检索证明对应文档有效命中；名称映射不替代 METRIC 有效命中。
- Top-K 是每个请求项的候选数，不是允许输出的指标数。其他相似候选只保留为证据。
- 某个已识别指标未进 Top-K 或未达到阈值，按该指标召回失败停止，不替换为相似指标。
- 每个请求内所有检索及映射固定使用同一个 asset_version。
- 保留 Dense-only（仅稠密检索）和一次 SQL 生成 LLM 调用；不增加 LLM 指标选择步骤。

每次最多 5 个去重后的请求指标。它是首版请求边界，与目前目录数量巧合一致；不能简单遍历“当前全部五个指标”作为选择逻辑。超限直接拒答，不截断。

## 5. 指标兼容检查

全部请求指标召回成功后，程序检查：

| 条件 | 通过规则 | 不满足时 |
|---|---|---|
| 数据来源 | 完整限定名相同且是同一个事实表 | 不支持该组合 |
| 日期口径 | 来源表列、目标日期表、日期过滤列一致 | 不支持该组合，即使用户没有日期条件 |
| 指标固定 filters | 确定性规范化后条件集合一致 | 不支持该组合 |
| 公式 | 已认证的直接物理字段聚合公式可解析 | 缺损资产或超出表达能力，按原因停止 |
| 用户范围 | 所有指标共享日期、分组和查询级条件 | 分别指定范围的请求不支持 |

filters 仅做受支持语法的结构规范化，如表别名解析、无意义括号、条件集合顺序及重复项；字符串常量保持原样。不通过 LLM、简单删字符或任意布尔等价推导认定两个口径相同。

不同固定 filters 不能用并集加到公共 WHERE 中，否则会改变每个指标的统计范围。首版不自动构造条件聚合或多子查询。

相同事实表不要求指标使用相同聚合函数：COUNT(DISTINCT order_id) 与 SUM(金额)可以在相同分组中并列计算，分别保留各自的粒度和去重规则。

## 6. 表列、关系及上下文

保留 TABLE → 候选表范围内 COLUMN 的主路线、现有分组维度补充召回和独立 METRIC 路线。TABLE 与指标路线可独立推进。

1. 所有指标共同 data_source 必须被 TABLE 有效命中，作为唯一事实锚表。指标定义不能直接补入未命中的事实表。
2. 分别提取各指标 formula、filters、time_field 引用，合并成必需字段集合；字段身份用完整表名和列名，不能只按列名去重。
3. COLUMN 仍仅在 TABLE 候选表中检索。允许受限的必需字段补充检索；必需字段不能被全局 Top-K 截断淘汰，也不能绕过有效 COLUMN 命中直接虚构加入。
4. 任意指标所需列缺失，整次停止。记录缺失字段及依赖它的请求指标。
5. 按已有确定性图规则连接分组及日期维度，共享路径去重。Join Key（连接键）来自结构事实，不由向量或模型猜测。
6. 聚合路径必须保持事实行不被重复放大；首版只接受结构事实能够证明的事实表到唯一维度键路径。可能导致一行变多行的连接不因“图上可达”就放行。
7. 日期关系由共同 time_field 绑定；右侧日期过滤字段不充当 Join Key。
8. 输出一份 Dynamic Schema（动态结构上下文）和包含全部请求指标的 Indicator Context（指标上下文）。共享字段只出现一次，每个指标的定义及公式独立保留。

同一请求的 TABLE、COLUMN、每次 METRIC 检索、名称映射、图及模型必须属于同一资产版本。加载新版本失败不能拼接旧版名称或公式继续。

## 7. 完整处理链路

~~~text
用户问题 + 一致的资产快照
  ├─ TABLE 检索（含现有分组补充召回）
  └─ 识别完整请求指标清单 → 每个指标独立 METRIC 检索
          ↓
  所有指标完整命中 → 同表、同日期、同固定条件检查
          ↓
  候选表内 COLUMN 检索 + 全部必需字段合并检查
          ↓
  共同锚表 → 确定性图连接 → Dynamic Schema + 全部指标上下文
          ↓
  一次 LLM 生成一条 SQL
          ↓
  候选表列范围检查 → AST SQL 安全校验
          ↓
  请求指标覆盖与口径检查（本规格新增，见第 8 节）
          ↓
  PostgreSQL 只读执行 → 一个结果集
~~~

所有 SQL 后置检查完成前不得访问业务数据库执行候选 SQL。

## 8. SQL 输出完整性与正确性

Prompt 必须明确：按用户请求顺序输出全部去重指标，不能少算、替换或增加未请求的指标；只使用给定完整公式，保留 COUNT DISTINCT、NULLIF、固定过滤及时间口径。用户指定范围作用于所有指标。不能回答全部请求时返回 CANNOT_ANSWER。

仅靠 Prompt 和表列范围检查不能保证这些要求。本规格增加受限的确定性检查，属于 Online Query 后置校验，不让 Retrieval 模块生成或解析模型 SQL。

首版多指标 SQL 形态限定为单层 SELECT + 共同 FROM / JOIN / WHERE + 可选 GROUP BY、ORDER BY、LIMIT，不包括 CTE、子查询、窗口计算、集合运算和 HAVING。该限制只针对新增多指标路径，不自动缩减既有单指标和实体路径。

确定性检查至少要求：

- 每个请求指标在最终投影中恰有一个对应表达式；按用户请求顺序输出，其他投影只允许合法分组字段。
- 解析表别名、投影别名并规范化后，与权威公式结构匹配。不能用“列名相同”“指标名字相同”或“引用字段相同”代替公式匹配。
- 首版仅允许预先定义并测试的结构规范化，不实现通用 SQL 数学等价证明。SUM(x-y) 与 SUM(x)-SUM(y) 不默认视为可互换，NULL 语义可能不同；Prompt 引导使用权威公式形态。
- 指标固定条件在共同过滤范围内强制成立，不能漏掉或被 OR 绕过；不能改变 COUNT(DISTINCT ...) 或去掉除零保护。
- 实际 Join 使用确定的图边和键，且不放大事实行；涉及日期时使用绑定日期路径。
- 输出维度与 GROUP BY 一致，所有指标共享同一分组及范围。

结构无法确认或覆盖/公式/固定条件/关系不符合时返回 SQL_REJECTED，数据库不执行。具体支持的表达式语法、归一化规则与校验职责在实现设计中验证；若无法提供可测试的最小实现，应回到规格讨论，不把这项承诺降成仅提示词约束。

该检查只保证已定义的受限契约，不宣称能确定性理解任意用户自然语言过滤条件。自然语言到分组与日期值的语义正确性仍须独立 AI Evaluation（AI 评测）及业务验收。

## 9. 输入、输出与失败行为

### 9.1 对外与内部契约

对外继续使用 question、可选 request_id；返回既有 QuerySuccess / QueryFailure。用户不能提交任意公式、集合、资产或指标定义覆盖业务事实。

内部成功结果继续使用已有 metrics 列表：只含全部请求指标，按首次提及顺序排列，不含自动展开的依赖指标或无关候选。

新增内部行为信息（名称为逻辑字段，具体类型留待实现设计）：

- 请求片段及其位置、规范指标身份、每项匹配原因。
- 每项检索证据、有效命中与失败原因、asset_version。
- 请求指标集合、共同数据来源/日期/固定条件、每个指标必需字段。
- 向 Online Query 传递用于检查的结构化指标约束，不能只拼接成 Prompt 后丢弃。

成功不变量：请求指标集合 = 最终 metrics 集合 = SQL 实际指标输出集合。实体类请求没有指标；单指标是集合大小为 1 的情况。

### 9.2 失败映射

| 情况 | 检索状态或内部原因 | 对外行为 |
|---|---|---|
| 列举项未登记或已识别指标召回失败 | NO_METRIC_HIT + 失败请求项 | CANNOT_ANSWER，整次停止 |
| 名称多义或列举意图不确定 | AMBIGUOUS | CANNOT_ANSWER，整次停止 |
| 超限、不同表/日期/固定条件、不同查询级范围 | 内部原因记录为 UNSUPPORTED_METRIC_COMBINATION | CANNOT_ANSWER，整次停止 |
| 必须表/列缺失或关系不可达 | 沿用对应资源失败状态 | CANNOT_ANSWER，整次停止 |
| Qdrant、向量模型或资产技术故障 | 沿用明确技术状态 | 多指标返回 CONTEXT_ERROR，见下文 |
| SQL 漏指标、改公式、越界或不安全 | SQL_REJECTED | 不执行 SQL |
| SQL 合法但结果无数据 | 既有成功空结果语义 | 不伪装成资源检索失败 |

不得把业务失败走静态 fallback（回退），不得返回部分成功结果。

技术故障规则：新增多指标路径暂不允许回退到全量静态上下文。现有静态路径不携带相同的请求覆盖与兼容约束，直接回退会绕过新契约。已能确定是单指标或实体的请求继续沿用原技术回退规则；无法加载指标映射且无法确认请求类型时，返回 CONTEXT_ERROR。

这是对基线“技术失败可静态回退”的条件收紧，已作为本次多指标规格决策接受。将来只有静态路径也能使用一致资产并完成全部多指标约束时，才讨论受控回退。

## 10. 验收标准

### 10.1 Software Test（软件测试）

| 编号 | 输入/故障 | 必须验证 |
|---|---|---|
| MM01 | C05 三指标 | 三个规范指标全部召回、进入上下文及结果 |
| MM02 | 只查毛利率 | 一个指标，不误选毛利 |
| MM03 | 毛利和毛利率 | 两个指标，长名称不吞掉独立短名称 |
| MM04 | 销售额、人民币销售额 | 按指标身份去重 |
| MM05 | C04 四指标及五指标请求 | 不受原 metric_top_k=3 总数限制 |
| MM06 | 名称映射多义、指标列举片段含未知项 | 停止，LLM/数据库调用数均为 0 |
| MM07 | 只召回两个所需指标、第三个未命中 | 停止，不返回部分结果 |
| MM08 | 某指标公式字段未召回 | NO_REQUIRED_COLUMN_HIT；不能用其他指标命中掩盖 |
| MM09 | 不同事实表、日期角色、固定过滤条件 | 拒绝组合；不合并 WHERE 或强行 Join |
| MM10 | 共同条件及日期 | 对所有指标使用同一口径 |
| MM11 | 重复路径、多日期边、导致重复计数的连接 | 合法边去重；歧义或放大风险停止 |
| MM12 | 动态发布、缓存或检索故障 | 单一资产版本；多指标不绕过新约束回退 |
| MM13 | 漏输出、改 COUNT DISTINCT、改公式或 NULLIF | SQL_REJECTED，数据库调用数为 0 |
| MM14 | 删除固定过滤、OR 绕过、错误 Join | SQL_REJECTED |
| MM15 | 别名/空格/括号变化及不支持的 SQL 形态 | 允许已定义等价形式，其余受控拒绝 |
| MM16 | 用户请求顺序变化、重复名称 | 输出顺序与去重契约正确 |
| MM17 | 维度列表、引用文本、否定或分别日期表达 | 不从无关位置提取指标，不静默漏项 |
| MM18 | 超过 5 个不同指标 | 使用隔离测试资产，验证超限而非未知指标 |
| MM19 | 单指标、实体查询、安全拒绝、无数据 | 保留适用的既有行为 |

用隔离测试数据验证 NULL、零分母、同一订单多明细和不同分组；不修改真实业务数据来制造坏案例。

### 10.2 AI Evaluation（AI 评测）

使用真实 BGE-M3、Qdrant、LLM 和只读 PostgreSQL，必须通过正式在线服务组装路径，记录实际是否发生回退。

- 现有 20 题逐题复测；C01/C03/C04/C05 都按正式多指标契约评估，C05 必须由拒答转为正确返回。
- 增加同义别名、指标次序变化、分组/日期变化、部分指标未知、口径冲突的独立样例。
- 同时记录请求指标集合准确性、每个指标召回结果、必需字段覆盖、SQL 结果等价、拒答原因、实际模式、耗时和调用次数。
- 正向范围内问题要求全部请求指标及业务结果正确；负向样例必须按约定停止。执行成功、无异常或结果碰巧相同不单独算契约通过。
- 固定验收集目标为全部通过，保留真实失败记录；不通过移动失败案例到“范围外”改善通过率。

### 10.3 Business Acceptance（业务验收）

C05 按客户类型返回三项结果：订单按 order_id 去重，销售额汇总冻结人民币净金额，毛利率按同范围总毛利除以总销售额；仅统计完成状态，使用完成日期口径。与人工审核的标准 SQL 逐组比较。
