# RAG Offline Build Module Spec

## 1. 模块目标

RAG Offline Build（RAG 离线构建）负责把已确认的数据库结构和指标事实转换为可供后续在线检索使用的离线产物。

本模块只构建检索知识，不生成 SQL、不执行查询、不修改数据库。

## 2. 范围

本模块负责：

1. 加载并校验表、字段、关系和指标四类事实源。
2. 将字段值示例作为字段属性处理。
3. 生成 TABLE、COLUMN、METRIC 三类检索文档，并分别写入三个独立的向量集合。
4. 根据外键事实生成确定性的 Relationship Graph（关系图）。
5. 对三类文档的正文调用 Embedding（向量化）能力，并将正文向量和元数据写入对应集合。
6. 校验完整产物后一次性发布。
7. 返回明确的构建成功或失败结果。

## 3. 输入事实源

输入只包含：

- `src/structure/generated/tables.json`
- `src/structure/generated/columns.json`
- `src/structure/generated/relationships.json`
- `src/semantic/metrics.json`

这些文件是离线构建的 Authoritative Source（权威事实源）。生成的检索文档和向量索引不是业务事实源。

### 3.1 字段值契约

`column_values.json` 不再作为独立输入。完成字段值迁移后必须删除该文件，离线模块不得保留兼容读取分支。

字段值示例直接保存在对应的 `columns.json` 字段记录中：

```json
{
  "schema_name": "mart_sales",
  "table_name": "fct_sales_order_line",
  "column_name": "order_status",
  "description": "订单状态",
  "value_examples": [
    "cancelled",
    "completed",
    "confirmed",
    "pending"
  ]
}
```

规则：

- `value_examples` 为可选字符串数组。
- 没有值示例的字段使用空数组或省略该属性。
- 数组中的空字符串和重复值无效。
- `value_examples` 用于帮助理解字段语义，不代表数据库中全部合法值。
- 高基数字段不得导出全部取值。

## 4. 核心对象

### 4.1 TABLE Document（表文档）

表达一张表的身份、业务含义和适用场景，用于回答“应该查询哪些表”。

每张表必须生成且只能生成一份 TABLE Document。

### 4.2 COLUMN Document（字段文档）

表达字段所属表、字段名称、数据类型、业务含义、键属性和字段值示例，用于回答“应该使用哪些字段”。

每个字段必须生成且只能生成一份 COLUMN Document。

### 4.3 METRIC Document（指标文档）

表达指标名称、别名、定义、公式、数据来源、依赖指标、时间字段、过滤条件和注意事项，用于回答“指标应该怎样计算”。这些信息分成向量正文和结构化元数据两种表示：向量正文用于找到指标，结构化元数据用于保留完整业务事实。

每个指标必须生成且只能生成一份 METRIC Document。

指标 SQL 模板可以保留在权威事实源中，但离线产物不得把它转换成可直接执行指令。

### 4.4 Relationship Graph（关系图）

关系图表达真实表之间的确定性连接方式。

规则：

- Foreign Key（外键）记录形成 Join Edge（连接边）。
- Primary Key（主键）和 Unique Constraint（唯一约束）用于校验关系端点。
- 关系不得通过向量相似度或 LLM 推测。
- 关系图不进入向量索引。
- 每条连接边必须保留两端表名、字段名和关系类型。
- 同一对表存在多条关系时，必须全部保留，不得自行合并或选择。

### 4.5 三个向量集合

三类检索文档必须分别写入三个独立的向量集合，不使用一个混合集合作为默认检索入口：

| 向量集合 | 文档类型 | 主要回答的问题 |
|---|---|---|
| TABLE Collection | TABLE Document | 应该查询哪些表？ |
| COLUMN Collection | COLUMN Document | 应该使用哪些字段？ |
| METRIC Collection | METRIC Document | 指标应该怎样计算？ |

规则：

- V1 固定三个逻辑集合和三条检索路由。
- 每条路由只检索对应集合；需要跨集合协作时由在线编排显式调用，不由向量库自行混合。
- 具体向量数据库、物理集合名称和目录属于实现设计，不改变这三个逻辑集合的边界。
- Relationship Graph（关系图）是独立的结构化产物，不属于任何向量集合。

### 4.6 文档正文、向量和元数据

每份检索文档由三部分组成：

Document
├─ document_id：稳定且唯一的文档身份
├─ page_content：参与 Embedding 的自然语言正文
└─ metadata：不参与 Embedding 的结构化元数据

page_content 用于语义相似度检索；metadata 用于精确身份识别、集合路由、候选表过滤和后续关联。表名、字段名、指标名等身份信息可以同时出现在正文和元数据中：正文帮助语义匹配，元数据保证精确过滤。

各类文档的划分：

| 文档 | 进入 page_content 并向量化 | 放入 metadata，不作为向量正文 |
|---|---|---|
| TABLE | 表名、表的业务描述、表类型或用途说明 | doc_type、schema_name、table_name、原始 table_type |
| COLUMN | 表名、字段名、字段描述、数据类型的可读表达、主外键语义、低基数字段的 value_examples | doc_type、schema_name、table_name、column_name、原始 data_type、空值属性、主键/外键标志 |
| METRIC | 指标名、别名、定义、指标层级等用于识别指标的业务语义 | doc_type、指标名、别名、指标层级、定义、公式、数据来源、时间字段、过滤条件、直接依赖指标标识、注意事项 |

补充规则：

- value_examples 必须进入 COLUMN 文档正文，帮助召回“已完成”“华东”“产品线”等表达；它仍然只是示例，不代表全部合法值。
- Metric 的公式、数据来源、时间字段、过滤条件、依赖指标和注意事项属于结构化业务事实，不进入 Metric 的向量正文；它们必须完整保存在 metadata 中。指标名、别名和定义可以同时存在于正文和 metadata 中。
- sql_template 保留在指标权威事实源中，不作为可执行指令写入向量正文；如后续在线模块需要它，应按已检索到的指标身份受控回查。
- Relationship Graph 的表、字段、约束和连接边全部以结构化字段保存，不生成向量正文。

## 5. 构建行为

离线构建必须按以下逻辑完成：

```text
加载事实源
→ 校验输入契约
→ 生成 TABLE、COLUMN、METRIC 文档
→ 分别向量化并写入三个向量集合
→ 生成确定性关系图
→ 校验离线产物是否可重新加载
→ 发布完整产物
```

构建应满足：

- 相同事实源可以安全重复构建。
- 每类文档只能写入对应的向量集合。
- 同一类文档在一次构建中使用一致的 Embedding 配置，向量维度必须与目标集合兼容。
- 构建过程中不能覆盖当前可用产物。
- 只有全部步骤成功后才能发布新产物。
- 构建失败时，当前已发布产物保持不变。
- 源文件不增加业务版本字段。

### 5.1 向量集合和关系图的加载契约

本模块只定义离线产物如何被写入、校验和交付；在线检索模块的具体实现另行设计。

构建端必须：

1. 为每类文档生成 page_content、metadata 和稳定的 document_id。
2. 只将 page_content 发送给 Embedding；将生成的向量、metadata 和 document_id 一起批量写入对应集合。
3. 分别重新加载 TABLE、COLUMN、METRIC 三个集合，校验集合可用、文档数量正确且至少可以完成一次检索。
4. 将关系图以结构化邻接数据交付，确保表、字段和连接边可以被确定性遍历。

在线消费端应：

1. 启动时连接已发布的三个向量集合，并分别建立 TABLE、COLUMN、METRIC 三条检索路由。
2. 查询时只向对应集合发起检索，不把整个向量集合全部加载到应用内存。
3. 单独加载关系图的结构化数据；根据候选表执行确定性路径遍历，返回 Join 边或 Join 路径。
4. 将向量检索结果和关系图结果交给在线编排，生成精简 Schema；集合不可用、无法重新加载或配置不兼容时，交由在线模块按其契约处理回退或失败。

集合名称、向量库客户端、Embedding 模型、向量维度、距离算法、持久化目录和具体加载 API 属于实现设计，不属于本模块的行为契约。

## 6. 输出契约

成功构建必须产生：

- 可独立检索的 TABLE 向量集合。
- 可按候选表限制范围的 COLUMN 向量集合。
- 可独立检索并保留指标依赖的 METRIC 向量集合。
- 可加载并确定性遍历的关系图。
- 构建结果摘要。

构建结果摘要至少包含：

- 构建状态。
- 表文档数量。
- 字段文档数量。
- 指标文档数量。
- 关系边数量。
- 三个向量集合是否可以重新加载。
- 是否已发布。
- 失败记录数量。
- 失败时的错误分类和错误信息。

离线模块不得输出 SQL 或查询结果。

## 7. 失败规则

出现以下任一情况，构建必须失败且不得发布半成品：

- 输入文件缺失、无法读取或不是合法 JSON。
- 输入集合为空。
- 表、字段或指标身份重复。
- 字段引用不存在的表。
- 字段值示例类型错误。
- 外键任一端的表或字段不存在。
- 指标依赖不存在的指标。
- 指标引用不存在的表或字段。
- Embedding 调用失败。
- 向量维度与目标集合不兼容。
- 任一向量集合写入或重新加载失败。
- 文档数量或关系图校验失败。

错误必须可定位到具体资源和记录，不得静默跳过非法事实。

## 8. 验收标准

### 8.1 Software Test（软件测试）

- 四个事实源可以成功加载。
- `columns.json.value_examples` 可以正确校验和进入字段文档。
- TABLE、COLUMN、METRIC 文档数量与对应事实源一致。
- 三个向量集合彼此独立，且每份文档进入正确集合。
- page_content 和 metadata 按契约生成，value_examples 能进入 COLUMN 文档正文。
- Metric page_content 不包含公式、数据来源、时间字段、过滤条件、依赖指标或注意事项；Metric metadata 完整保留这些事实。
- 每份文档具有稳定且唯一的身份。
- 所有字段、指标引用和关系端点均能通过校验。
- 构建产物能够持久化并重新加载，三个集合和关系图都可以被在线模块加载。
- 重复构建不会产生重复文档。
- 任一步骤失败都不会发布半成品。

### 8.2 Retrieval Evaluation（检索评测）

- 固定问题能够召回预期表。
- 字段检索能够在候选表范围内召回预期字段。
- 指标问题能够召回预期指标及其直接依赖。
- 字段值示例能够帮助召回状态、地区、产品线等字段。
- 关系图能够返回真实存在的连接边。
- 多日期关系必须完整保留，不得错误固定为单一日期字段。

### 8.3 完成条件

满足以下条件，离线模块才可以进入 Online Retrieval（在线检索）设计：

- 所有必需软件测试通过。
- 离线检索评测通过。
- 构建失败和发布保护经过验证。
- 构建结果摘要能够明确说明成功数量、失败数量和发布状态。
- 未修改数据库结构和业务数据。

## 9. 不在本模块范围内

- 在线问题检索流程。
- Prompt 组装。
- LLM SQL 生成。
- SQL Guard。
- PostgreSQL 查询执行。
- 直接连接或扫描数据库生成事实源。
- FastAPI 和 Streamlit 修改。
- 多轮会话和会话存储。
- 用户、租户、登录和权限。
- 网关、限流和可观测平台。
- 经营分析 Agent。
- Hybrid Search（混合检索）、Reranker（重排序）和 Multi-query（多查询扩展）。
- 具体向量数据库、Embedding Provider（向量服务商）、目录和代码结构选择。
