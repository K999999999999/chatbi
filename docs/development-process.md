# ChatBI 开发流程导航

## 用途

当需求不明确、思路混乱或不知道下一步做什么时，查看本文档。

判断原则：

> 从第一步开始检查，最早一个没有满足“完成标志”的阶段，就是当前阶段。

不要跳过当前阶段，也不要同时展开后面多个阶段。

## 企业开发顺序

| 阶段 | 核心问题 | 最小产物 | 完成标志 |
|---|---|---|---|
| 1. Requirement（需求确认） | 解决什么问题，做什么，不做什么，怎样算成功？ | 产品范围或需求说明 | 目标、范围、非目标和验收标准明确 |
| 2. Architecture（架构设计） | 系统有哪些模块，主链路是什么，边界和依赖是什么？ | 架构说明 | 模块职责、协作关系和技术边界明确 |
| 3. Module Spec（模块规格） | 当前模块必须表现出什么行为？ | 模块规格 | 输入、输出、规则、错误、不负责范围和验收标准明确 |
| 4. Implementation Design（实现设计） | 当前模块具体怎样实现？ | 简短实现方案 | 内部链路、代码落位、外部依赖、关键类型、技术选择和测试方式明确 |
| 5. Design Review（设计审查） | 实现方案有没有违背需求、架构、规格或真实项目？ | 审查结论 | 阻塞问题已解决，过度设计已删除，可以安全编码 |
| 6. Task Split（任务拆分） | 怎样拆成可以独立开发和验证的小任务？ | 任务清单 | 每个任务的目标、范围、依赖和完成标准明确 |
| 7. Implementation（编码实现） | 按任务怎样完成代码？ | 代码和对应测试 | 当前任务实现完成，相关测试通过 |
| 8. Test / Evaluation（测试与评估） | 程序、AI 行为和业务结果是否正确？ | 测试与评测结果 | Software Test（软件测试）、AI Evaluation（AI 评测）和 Business Acceptance（业务验收）分别完成 |
| 9. Code Review（代码审查） | 改动是否正确、简洁、安全且没有超出范围？ | 审查结果 | 问题已修正，差异和验证结果符合要求 |
| 10. Integration / Release（集成与发布） | 怎样接入、部署、监控和回滚？ | 发布记录 | 集成验证通过，发布与回滚方式明确 |

## 快速判断自己在哪一步

- 连“要解决什么问题”都说不清：回到第 1 步。
- 需求清楚，但不知道系统怎么拆：处于第 2 步。
- 模块确定，但输入、输出、规则或错误不清楚：处于第 3 步。
- 模块行为清楚，但不知道代码怎么写、技术怎么选：处于第 4 步。
- 实现方案已经有了，但还没检查是否正确或是否太复杂：处于第 5 步。
- 方案确认了，但不知道先开发哪一块：处于第 6 步。
- 任务已经明确：进入第 7 步逐个实现。
- 代码完成，但没有完整正确性证据：处于第 8 步。
- 测试通过，但改动还没有正式检查：处于第 9 步。
- 所有检查通过，但还没有接入或发布：处于第 10 步。

## 模块、节点和任务的关系

- Module（模块）：一个完整业务能力，例如 Online Query（在线查询）。
- Node（节点）：模块内部链路的一步，例如 Prompt（提示词）组装、LLM 调用、SQL Guard（SQL 安全检查）和数据库执行。
- Task（任务）：一次可以独立完成和验证的开发工作。一个节点可以是一个任务，也可以拆成多个任务。

不是每个节点都需要单独写 Module Spec（模块规格）。通常一个模块一份规格，确认实现方案后再拆任务。

## 思路混乱时的处理方式

1. 暂停新增代码和技术选型。
2. 依次查看产品范围、架构和当前模块规格。
3. 找到最早没有完成的阶段。
4. 只解决该阶段的问题。
5. 如果一个待定问题会改变范围、行为或架构，先确认再继续。
6. 如果不会改变这些内容，采用最简单可验证的方案推进。

## 维护规则

- 阶段发生变化时，只更新“当前项目位置”。
- 需求或架构改变时，先更新对应事实文档，再更新当前状态。
- 不为每个小节点创建长文档；只有稳定契约、关键决定和验证结果需要保留。
- 文档状态必须以真实代码、测试和评测结果为准，不能把计划写成已经完成。
