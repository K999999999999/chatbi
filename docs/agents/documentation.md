# 文档维护规则

本文规定文档的职责、更新与检查方式。产品与架构事实仍以对应事实源为准；这里不复制它们的内容。

## 文档归属

| 文档 | 维护内容 |
| --- | --- |
| `README.md` | 人类阅读入口、项目简介、简短代码地图和正式文档导航。 |
| `AGENTS.md` | AI 协作的稳定强制规则和事实源入口。 |
| `docs/architecture.md` | 当前系统结构、模块职责、依赖方向和关键链路。 |
| `docs/product-scope.md` | 当前能力、支持场景和产品限制。 |
| `docs/specs/` | 当前行为与验收 Contract；同一规则只维护一份权威定义。 |
| `docs/designs/` | 理解或维护当前实现所需的重要机制，按需保留。 |
| `docs/runbook.md` | 当前安装、运行、测试、评测和故障处理步骤。 |
| `docs/roadmap.md` | 当前阶段、已确认方向、依赖和优先级确认状态。 |
| `docs/agents/` | ChatBI 特有的协作、领域、工作项、交付和文档维护规则。 |
| `docs/audits/` | 项目级审计报告及其基线、发现和证据边界；不定义产品行为 Contract。 |
| `.scratch/` | 工作规划、过程、历史决定、旧方案和历史验收。 |

新工作的 Spec、Design、Ticket 和过程记录可以先保存在 `.scratch/`。功能交付后，当前行为 Contract 应归入正式 Spec；历史方案或验收留在所属工作记录，不作为当前唯一规则入口。项目级审计报告可归档到 `docs/audits/`，并明确审计基线及证据边界。

## 更新与归档

- 行为、支持范围或实现机制变化时，更新各自事实源及受影响的测试、Evaluation 或验收入口；其他文档链接权威定义，不复制完整规则。
- 只有已确认目标、依赖、验收方式或完成事实改变时才更新 Roadmap。可依据证据修正过期事实；优先级调整、新增承诺或范围变化须先确认。已完成的阶段过程和历史结果留在工作记录，并绑定当时的 Commit、案例集与资源。
- 归档或移除入口前，逐项确认现行规则已迁移、独有历史内容有保留位置，且所有引用均已修复。不能确认覆盖时保留原文并记录原因。
- 标题按层级连续组织，不跳级；正文用带含义的 Markdown 链接定位章节，不使用 `§` 加数字作为跨章节引用。命令、源码片段和用于说明语法的行内代码可照常展示。
- 新增文档入口时同步更新 README 或 AGENTS 中对应导航。不要为满足目录形式创建空文档。

## 检查与 Review

本地与 CI 使用同一个组合检查入口：

```bash
uv run --python 3.11 --locked python -m scripts.check_documentation
```

组合检查校验全仓 Git 已跟踪及未忽略 Markdown 的本地链接；标题层级和正文章节引用只检查 README、AGENTS、已存在的 CONTEXT / CONTEXT-MAP 与 `docs/**/*.md`。工作记录仍接受链接检查，但不套用当前正式文档的结构规则。

需要单独检查链接时，原入口 `python -m scripts.check_markdown_links` 继续可用。完整门禁及其边界见 [Runbook 测试章节](../runbook.md#3-验证与ci)。

PR 的 Done When 与 Agent Review 应记录适用的文档更新位置，或说明不适用理由；还需核对历史去向、入口链接和路线图事实。自动门禁只验证确定性结构，不判断业务含义、事实是否过期或不同文档之间的语义一致性，这些仍由 Review 对照 Architecture、Product Scope、Spec 和验证证据完成。
